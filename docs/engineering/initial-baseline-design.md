# Strixnova 初始基线设计

本说明整理已确定的建设范围与实现选择，供初始候选审阅。它引用现有产品、领域、架构及工程材料，不另建权威或状态。范围确认与实际结果接受是两个阶段；当前验证和未完成项以[验证状态](validation-status.md)及原始证据为准。

## 目标与交付边界

Strixnova 是独立的开发中项目。展示名为 `Strixnova`，软件版本为 `0.1.0.dev0`。发行包、Python 导入包、命令和唯一 Skill 均名为 `strixnova`；项目配置是 `strixnova-project.yaml`，私有状态位于 `.strixnova/`。协议命名空间采用 `strixnova.*`，环境变量和专属规则身份采用 `STRIXNOVA_*` 与 `STRIXNOVA-GOV-*`。

初始交付包含当前运行代码、随包资源、Skill、审阅材料、构建安装工具、有效行为测试、当前工程材料和本候选真实形成的证据。完整公开合同、Authority、活动库和证据格式分别从 v1 开始。发行版本、格式版本、内容摘要和成熟度是不同概念。

保留产品当前的确认、工程评估、实施切片、验证、真实回执、本地 Git、多仓库协作、独立历史查询、事务恢复、维护互斥与受管安装能力。历史查询读取本产品当前格式生成的记录；软件维护保留检查、备份、停止、验证、切换和恢复，不预建其他格式的转换机制。

交付不包含已有数据或仓库历史导入、跨品牌转换、命令别名、双配置名查找、双格式读取或兼容包装。宿主现有安装、其他项目、公开包登记、域名、官网及远程发布不在本次实现范围。项目不使用自身管理本次开发，不建立相应 WorkItem。CI、hooks、WebUI 和额外插件不属于本次建设。

## 设计选择

| 关注点 | 采用的方案与理由 | 对应实现或约束 |
| --- | --- | --- |
| 独立产品身份 | 生成端、消费端、结构合同、安装元数据和安全归属同时使用唯一命名，避免一个产物拥有互不一致的身份 | 包入口、Schema、路径、Git 分支、安装回执和测试协议同步 |
| 完整 v1 | 以当前完整结构直接初始化，逐项确定当前合同，不把所有版本数字无差别替换 | 新数据库直接创建完整表、索引与写入保护；不识别的格式明确拒绝 |
| 现有模块边界 | 沿用单一应用协调、独立权威读取、确定性治理、只读投影及外部执行职责 | [目标模块](../architecture/modules.yaml)、[关系](../architecture/relationships.yaml)、[约束](../architecture/constraints.yaml) |
| 历史与恢复 | 保留新产品自身的真实历史与通用恢复能力；不从缺失数据推测既往结果 | 原始回执、精确提交、写入意图、文件摘要和停止证据各自保留来源 |
| 交付身份 | clean wheel 从临时源码快照构建，按字节核对资源；一次性隔离环境只检查安装态 | 源码测试、wheel、安装、Git 检出和 Agent 加载分别提供证据 |
| 依赖和开发入口 | 使用现有锁定依赖及仓库 Python 3.12，不顺带升级依赖或增加自动化平台 | `requirements-dev-win-py312.txt`、运行锁和 `scripts/local_validation.py` |

上述选择属于初始基线。本说明保留这些长期取舍；当前没有需要另立 ADR 的新模块机制。今后改变权威方向、持久格式或公共接口时，再按工程政策记录具体决策，不以本说明替代正式权威修订。

## 影响、风险与控制

命令、导入、配置路径和公开协议会影响调用方式；文档、Skill 与安装器必须使用同一合同。新库初始化和格式拒绝影响数据行为；格式不符时应保留原始文件，不能尝试转换、回填或清空。安全边界必须随路径一起变更，包括私有目录、符号链接、工作树归属、SQLite 写入保护、验证命令政策和清理范围。

| 风险 | 保留的设计控制 | 验证与限制 |
| --- | --- | --- |
| 不受管路径或工作树被误处理 | 路径限定、普通文件检查、仓库身份、创建归属和分支前缀共同校验 | 定点功能回归及本地 Git 夹具；未取得宿主能力的检查保持跳过记录 |
| 验证或维护中断后重复产生效果 | 持久写入意图、真实进程回执、互斥与恢复入口 | 保留真实中断及停止事件，恢复复用原始结果；不把模拟状态当原始执行 |
| 包、Skill 与运行代码不一致 | 分别绑定源码资源、Skill 内容、wheel 和实际安装身份 | clean wheel、隔离安装及原生加载证据；版本号相同不代表字节相同 |
| 测试结果被扩大为语义接受 | 程序、Agent 与负责人职责分开；失败、跳过、待验和限制可见 | 确定性检查不决定语义，真实 Antigravity 独立复核不代替负责人接受 |
| 交付过程混入既有内容或未授权副作用 | 新目录、新环境、新证据；真实仓库在结果确认前不暂存或提交 | 本地 Git 状态单独检查；不操作其他项目、现有宿主安装或远端 |

用户行为和文档支持由新命令、公开合同及唯一 Skill 承担；产品和领域的有效职责继续保留，架构不增加并行系统。质量与性能采用当前测试和有界查询机制，本次未形成新的性能保证。安全、隐私、供应链和部署运维的结论限于明确受检的输入与环境，不构成外部认证。

## 验证和交付

源码验证使用仓库根解释器和本地验证入口；按影响完成定点、快速和全量回归，保留失败及修复后的结果。工程材料检查核对归属、依赖、责任和实际绑定。只有 clean wheel 入口提供构建证据，随后在一次性隔离环境检查运行依赖、包资源和命令。

Agent 场景按[已确认的隔离方案](agent-acceptance.md)使用固定输入；候选尚未形成或独立复核存在阻断时不得投递接受输入。场景停止后保留失败或待验，继续不依赖该场景的工作。结果、记录和当前依赖见[验收目录](../../tests/acceptance/guided-formation-cases.yaml)。

实际结果审阅前，真实仓库保持未暂存、未提交，工程材料保留草稿和未完成绑定。负责人确认后才组织原子提交，再用真实提交及祖先关系补齐 Git 绑定，执行相应检出和仓库检查。不得填写假提交、把空绑定解释为已采用，或把隔离测试接受解释为真实仓库提交与发布授权。

候选使用受管安装时，进入条件、停止证据、维护互斥、备份、验证和恢复由现有维护流程约束；具体步骤见[历史查询与自身升级](../使用说明/历史查询与自身升级.md)。初始交付不对任何现有宿主执行安装切换。第三方来源和许可仍由根 README 集中维护。
