# 实现观察提供者能力矩阵

本文说明当前源码实际具备的实现观察能力及其边界。它是适配器能力与验收说明，不是产品、领域或目标架构权威；“支持某语言”也不等于对任意该语言项目天然完整。

## 统一结果

所有内置和外部提供者都投影为 `strixnova.implementation-observation.v1`：精确观察范围、具有稳定逻辑身份的源码/项目/构建节点、全部实际关系、解析状态、配置条件、能力、覆盖、限制、缺口、观察路径哈希和回执。实现对齐只消费这一结果，不直接认识每种 AST、编译器或构建系统。关系底账保留内部、外部、未解析和歧义关系；同一文件上的多个构建目标也不会合并成自环。

覆盖状态按“范围 + 语言 + 配置 + 必需关系种类”计算：

- `complete`：实际发现源码，提供者支持全部必需关系，并且没有限制或缺口；
- `partial`：已经取得部分事实，但存在能力限制、未解析、歧义或遗漏风险；
- `unavailable`：没有可用提供者、没有本次执行授权，或精确快照不能供该提供者执行；
- `failed`：范围读取、语法解析、受控进程或输出合同失败。

任何非完整状态都会阻断受影响范围的完整实现对齐，但不会阻止智能编码代理继续阅读源码、领域文档并与用户讨论。此时结论必须明确哪些实现事实没有被机器完整观察。

## 当前内置适配器

| 语言/生态 | 当前静态来源 | 可观察关系 | 已知完整性边界 |
| --- | --- | --- | --- |
| Python | 标准库 AST、软件包相对路径 | 源码导入 | 动态导入形成缺口；源码容器不能冒充单包根；生成模块、插件发现和运行时装配需要补充证据。 |
| Rust | `mod`、`use`、`Cargo.toml` | 模块引用、包依赖 | `cfg`、feature、工作空间继承、过程宏和 `build.rs` 影响出现时需要按配置补充 Cargo/rust-analyzer 等授权观察。 |
| Go | 源码 import、多个 `go.mod`、`go.work`、本地 `replace` | 包导入、模块依赖 | 常见多模块和本地替换可保持内部关系；build tags、平台文件选择、生成代码、复杂替换和工具链解析影响出现时需要按配置补充 Go 工具观察。 |
| TypeScript/JavaScript | import/export/require、workspace `package.json`、`tsconfig` 项目引用 | 源码导入、包依赖、项目引用 | 范围内具名 workspace 包保持内部关系；path alias、条件 exports、动态加载、bundler 插件和多 tsconfig 选择可能产生缺口，需要项目配置或授权工具补足。 |
| C# | `using`、`.csproj` 的项目/包引用 | 命名空间引用、项目引用、包依赖 | 内置结果固定为部分覆盖；完整类型绑定、条件属性、生成源码和 MSBuild 图需要按目标框架/配置授权 Roslyn、MSBuild 或等价结构化提供者。 |
| C/C++ | `#include`、CMake 目标与链接声明 | 源码包含、构建目标依赖 | 内置结果固定为部分覆盖；宏展开、include path、条件编译、生成文件、平台/工具链和非 CMake 构建图需要 compile database、编译器或构建系统提供者。 |

内置适配器不执行项目代码、构建脚本、钩子或远程操作。它们只在实际遇到相关限制时报告缺口；C# 和 C/C++ 因核心语义天然依赖配置化工具链，当前始终诚实报告部分覆盖。

## 其他语言和更深观察

`ExternalObservationProvider` 可为任意语言或现有语言的更深层级提供观察。它不是 CLI（命令行界面）临时拼出的任意命令：Coding Agent（智能编码代理）必须在
`strixnova.engineering-assessment.v1` 中逐项提出，程序原样投影到
`strixnova.engineering-plan.v1`，再随完整工程方案由项目负责人确认。每项计划必须给出：

- 精确 `scope_id` 和 `language_id`；
- 稳定提供者身份与版本；
- 明确源码 glob；
- 完整 argv；
- argv 对应可执行文件、入口脚本，以及 provider 使用的配置和支撑文件的路径、角色与 SHA-256；
- 只允许该 argv 的用途专属 `ProcessPolicy`；
- 有限超时、清理时限和输入输出上限；输入最高 64 MiB，输出最高 256 MiB，项目应采用满足实际规模的更低值。

提供者从 stdin 接收范围、配置、范围文件和预期源码文件，向 stdout 返回
`strixnova.implementation-observation-provider.v1`，其精确字段由[外部提供者 JSON Schema](contracts/implementation-observation-provider-v1.schema.json)固定。核心会先解析已确认材料路径，核对它们确实绑定相应 command 参数，并在启动进程前重新计算每个可执行文件、入口脚本、配置和支撑文件的 SHA-256；缺失、替换或字节变化一律形成 `not_run` 失败。只有材料身份一致才启动进程，再按随安装包提供的同版合同校验输出，并重新验证提供者身份、逻辑节点键、路径边界、源码集合与真实 SHA-256、节点引用、关系种类与解析状态、证据位置、限制和缺口，最后把实际材料散列写入规范化回执。未授权时程序绝不启动命令；请求输入超限、非零退出、超时、输出过限、无效 JSON、合同错误或源码证据不完整都会成为失败结果。

外部提供者当前只针对工作树执行。不可变 Git 提交若没有被安全物化为独立工作区，会返回 `not_run`，不能拿当前工作树工具结果冒充历史提交证据。

首次形成或主动刷新外部观察证据时，安装态入口还要求本次
`--authorize-external`；它只授权已确认方案中的精确 provider，不接受替代 argv、路径、
glob 或策略。正式底账随后保存被观察路径的规范字节哈希；日常一致性门在没有提供者配置时，只能对这些路径及受管源码清单完全未变的已授权结果作精确回放。任一路径、源码集合或散列变化都会阻断并要求重新授权观察，因此普通产品门不需要永久持有可执行命令，也不会把旧回执当成变化后仍有效的证明。

工作树文件清单由 Git 的“已跟踪 + 未被忽略的未跟踪文件”产生，并受数量与输出上限约束；`node_modules`、`target` 等按项目 `.gitignore` 排除的依赖或构建目录不会被无边界递归扫描。非 Git 测试目录才使用有数量上限的文件系统回退。

## 安装态应用入口

安装后的唯一公开执行顺序是：

1. `strixnova alignment prepare` 绑定当前 `implementing` WorkItem（建设事项）、当前版本、已确认工程方案、当前实施切片和工作树，要求每个受管源码文件只落入一个受管作用域，运行内置观察，并写入不可变、内容寻址的小型清单及分页组件；
2. 仅当准备结果说明需要且工程方案已经包含精确 provider 时，调用
   `strixnova alignment capture-external --authorize-external`；
3. Coding Agent 通过 `strixnova alignment inspect` 顺序读取有界逻辑记录，沿不透明 `next_cursor` 取得冻结的长期权威上下文、架构事实、观察覆盖和精确 `semantic_decision`，不读取清单、组件或分页布局；
4. Coding Agent 把代码、领域文档、架构资料和用户讨论形成的语义判断按精确 `decision_ref` 提交给 `strixnova alignment write-candidate`；程序机械填充路径、散列、节点、关系、覆盖、回执、权威引用和代码版本，重新核对六个目标文件自 `prepare` 后没有被编辑，再用持久事务日志替换实现对齐根、四份底账和项目工程基线，并重新读取完整候选；任何最终校验失败都会恢复六个旧文件，提交前的进程崩溃由下一次入口自动恢复。

已有实现对齐的新修订只需要新 `ALIGNREV-` 身份及其精确
`supersedes_revision_id`，不重复提交现行观察范围或产物路径；首次建立才需要范围和路径。
准备清单和分页组件不进入长期权威，不产生可变“当前包”指针，也不改变 WorkItem 状态或版本。内容寻址组件跨准备包去重，Agent 只按逻辑页审阅大型多语言仓库。缓存维护不是普通工作流：负责人先执行 `strixnova alignment gc --dry-run`，接受精确孤立集合指纹后才可 `--apply`；程序只删除无任何 preparation/capture 清单引用的组件，不删除准备、捕获、事务或长期权威。

写入成功只表示 `candidate_valid=true`。候选始终是 `draft`（草稿）；只有覆盖完整、受管源码已对齐、依赖分类通过、目标责任已实现且没有偏离或未知时，才另外返回
`complete_alignment=true`。两者都不证明语义正确、生产可用、安全、普遍适用或已经发布，
`semantic_content_machine_proven` 始终为 `false`。最终采用仍只能随项目负责人接受精确实际结果后机械发生。

## 用于成熟项目的正确顺序

1. 根据仓库和构建资料枚举语言、源码根、包/工作空间、目标平台、构建配置和必须回答的关系种类。
2. 为每个边界建立精确观察范围；多包、多语言、多配置不压成一个模糊根目录。
3. 先运行无执行内置观察，保留所有部分、未解析和歧义结果。
4. 只对确实影响判断的缺口选择语言原生或构建工具提供者，把精确 provider 计划放入工程评估并随完整工程方案确认，再通过安装态入口逐次授权执行。
5. 用统一合同测试验证同一快照确定性、代表性结构、配置差异和失败不冒充空成功。
6. 智能编码代理将实现事实与领域文档、架构资料和用户讨论结合，形成领域候选、目标架构判断、归属、关系分类和偏离；工具输出本身不作这些语义决定。
7. 用 `prepare`、条件式 `capture-external`、逻辑 `inspect` 和 `write-candidate` 形成可恢复的完整草稿；只有所有必需范围完整、底账逐项复核且用户接受精确实际结果后，才能定档实现对齐。

因此，新增语言通常增加一个边界适配器和合同测试，不要求把该语言 AST 塞进 Strixnova 核心。真正较重的是为特定生态补足“项目/构建/配置语义”，这应按实际项目需要独立接入，而不是预先内置所有编译器。
