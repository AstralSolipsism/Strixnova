# 多仓库事项与整体方案

一个项目的一份事项库可以承载多个成员仓库的共同目标。方向、工程方案和实际结果各有一个整体接受；程序组合必要内容与验证证据，整体接受后按方案逐仓提交、合入和清理。Authority、工程基线和实现对齐从完整的当前 v1 合同开始；具体候选验证与宿主加载边界见[当前验证状态](../engineering/validation-status.md)。

项目声明和本机绑定按[配置与跨仓库权威读取](项目配置与跨仓库权威读取.md)准备。管理根可以独立于代码仓库；事项只写入该管理根的一份库，创建事项不为每个成员建立数据库或工作分支。管理库已有其他项目身份时拒绝写入。

## 形成整体方案

顶层 `investigation_ref` 选择配置仓库的不可变版本。工程评估 v1 的 `repository_scope` 另行声明各所需仓库的角色、调查版本和本地目标分支；程序解析并冻结各仓库自己的提交。缺少无关成员的检出不阻断本次计划。需要参与计划的仓库必须可定位；外部依赖只能声明为 read。

下面仅展示相关片段。身份和提交均须换成当前项目的真实值；完整评估字段以当前动作返回的输入合同为准。

```json
{
  "repository_scope": {
    "project_id": "PROJECT-1111111111111111",
    "repositories": [
      {
        "repository_id": "REPO-1111111111111111",
        "role": "modify",
        "investigation_ref": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
        "target_ref": "main"
      },
      {
        "repository_id": "REPO-2222222222222222",
        "role": "modify",
        "investigation_ref": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
        "target_ref": "main"
      }
    ]
  },
  "delivery_plan": {
    "expected_outcome": "前后端共同目标在整体结果接受后依次交付",
    "rollback_or_recovery": "保留实际已发生事实，再处理剩余动作",
    "limitations": ["各仓库独立合入，不承诺跨仓库原子提交"],
    "evidence_refs": ["direction"],
    "repository_order": ["REPO-2222222222222222", "REPO-1111111111111111"]
  }
}
```

操作、来源、验证命令及需定位的 ADR、领域事实变更和外部观察计划增加 `repository_id`。`path`、`to_path`、`cwd` 等仍在各自仓库内解释，不能借父目录或 move 跨仓库。不同仓库的同名文件及同名验证命令分别保留；同一仓库内的重复与冲突继续拒绝。只读范围不产生修改操作和交付责任。

单成员使用同一合同：只有仓库选择唯一时才能省略身份，程序在已校验方案中补全。没有声明的首次建项可以保持未绑定身份，按原建项流程形成声明；这不为过去记录补造身份，也不能用于多仓库范围。

切片仍通过事项内唯一的 `slice_id` 和操作引用表达依赖，可以跨越仓库。编译后的方案 v1 投影每个切片涉及的 `repository_ids`。`delivery_plan.repository_order` 必须恰好覆盖全部修改仓库，不能把只读依赖放入交付顺序。

方向和方案各按完整候选确认一次。需要提前独立交付的部分，应当先有独立验收目标并拆为另一个 WorkItem；同一事项没有按仓库分别接受结果的常规路径。

## 实施、验证与交付

例如将包含 title 和 request 的 JSON 保存为 `request.json`，从项目入口创建事项：

```powershell
strixnova --project-bindings .\bindings.json intake --project-dir D:\Work\project-entry --input '@request.json'
```

之后按照 `next` 返回的当前动作提交方向、整体工程评估并确认方案。在动作列出相应记录时，可读取：

```powershell
strixnova --project-bindings .\bindings.json next --project-dir D:\Work\project-entry --work-item-id WI-实际标识 --record repository_deliveries
```

`repository_deliveries` 包含方案绑定、调查提交、目标分支、操作/切片引用，以及实际工作区、提交、集成和收尾事实。记录存在本身不表示交付完成。`current_plan` 区分当前方案与保留的旧责任，整体完成由全部当前责任的实际结果推导。

方案接受后按 CurrentAction 准备各修改仓库的工作区，再按整体切片实施。验证命令的 `repository_id` 选择执行仓库，`input_repository_ids` 声明实际输入；只读依赖在声明版本的隔离副本中执行，不在依赖检出目录写入。存在保留的原生冲突时，该仓库使用已记录的目标目录；其他仓库仍使用自己的工作区。

实际结果的长期产物引用同时限定仓库和内部路径。内容或必要依据变化会使相应证据失效；负责人接受精确整体结果后，Agent 才组织各仓提交。未变化结果不会因下一仓开始交付而再次要求确认。

没有后端源码时，可以在已确认验证命令中声明 `dependency_checks`，记录实际版本、契约摘要、环境和有效期。命令取得真实观察后输出 `STRIXNOVA_DEPENDENCY_EVIDENCE=` 证据行；仅有地址或 HTTP 成功不能证明版本或后端源码覆盖。未知、不匹配和过期保留为受阻或限制，不能扩大为完整通过。完整输入格式见同版 Skill 的 verification 参考资料。

## 恢复、重规划与取消

工作区建立、验证和元数据修改先记录原意图；回写中断后按原仓库、命令与意图恢复，不能独立重跑未知结果的命令。已合入仓库的内容和原定档证据随历史保留。原事项尚未完成时，新整体方案可以开启该仓库的下一轮工作，旧合入不会被覆盖或自动回滚。

部分合入后取消，保留“该仓已合入、剩余工作未交付”的事实。未交付改动按负责人明确处置保留、移交或丢弃；仍在运行或结果未知的操作必须先收口。取消不等于撤销已合入内容，也不等于整体交付完成。

首次建库和运行维护都核对明确项目归属与当前格式，保留合法安装材料。单成员和多成员采用同一合同，不合并独立项目数据库；分离管理位置的维护组合须核对具体范围，不能由多仓库交付可用推导为已经验证。
