# 故障处理说明

## 先读 CurrentAction

绝大多数 `invalid_transition` 表示调用方在编排内部步骤。运行 `strixnova next --work-item-id <ID>`，按唯一 CurrentAction 选择普通事项入口。项目级权威使用 `status` 或 `authority`，外部活动使用 `activity`；不要把它们伪装成普通事项输入，也不要修改 Authority 数据库或伪造版本。

## authority_conflict 或 stale_version

同一 WorkItem 已被其他进程推进。重新读取当前 version、状态和动作，确认旧输入是否仍适用，再提交。不同 WorkItem 可以并行；同一 WorkItem 不接受过期写入。

## unsupported_authority_format

停止写入，先区分程序版本和数据格式。当前构建只支持已声明的精确格式，不匹配、未知或损坏的数据保持原文件并明确拒绝。不要删除数据、改写格式标记或重建状态来绕过保护。源码、Git 历史、ADR 和项目工程材料都不属于临时 Authority。当前程序组合的维护与恢复见[维护说明](历史查询与自身升级.md)。

## existing_work_unresolved

主工作树已有脏文件。Strixnova 不自动 stash，也不把这些文件归入新 WorkItem。先由用户或 Agent明确归属并处理，工作树干净后再开始实施。

## target_ref 或 worktree 错误

正式实施要求项目目录就是 Git 根、本地 target_ref 存在。单项建设时主工作树必须干净并检出目标分支；主工作树正在承载另一事项时，新并行事项必须明确提供仓库外、尚不存在的 worktree 路径。

## uncommitted_result

用户已确认实际结果，但 Agent 尚未把本事项文件形成原子提交。显式检查 diff，只暂存本事项文件并提交；不要使用无边界全量暂存。

## integration_conflict

这是原生 Git 内容冲突，不是 Strixnova 状态损坏。Agent 使用 Git 查看和解决：

1. 判断冲突解决是否改变用户可见结果或已确认方向/方案；
2. 用 `submit` 记录判断、具体理由和受影响的 `retest_command_ids`；
3. 解决冲突后运行受影响验证；
4. 用 `verify` JSON 输入的 `execution_area=target` 在本地目标工作树逐项验证；
5. 结果变化或复测出现 failed、blocked、not_run 时，用 `delivery` 重新展示实际结果并取得确认；纯保持原结果且复测通过时不新增确认；
6. 由 Agent 完成当前原生 Git merge commit，再次用空对象调用 `delivery` 核验、记录和清理。

Strixnova 不提供语义自动合并。

若冲突同时改变方向或工程方案，先按 CurrentAction 修订工程评估并重新确认方案；不要在确认完成前提交 merge。`merge_commit_required` 表示用户已经确认当前结果，但 Agent 尚未完成这个原生 merge commit。

## conflict_reverification_missing

冲突判断已经记录，但没有新的验证回执。运行计划中的受影响命令；确实不能运行时记录 not_run 和原因。旧回执不能证明冲突解决后的代码。

## verification_incomplete

至少一条方案命令没有回执，或最新回执明确需要重测。按 CurrentAction 列出的 verification 记录读取 missing_command_ids 和 retest_required_command_ids，补齐后再生成 ActualResult。

## failed、blocked 与 not_run

它们不是 Authority 故障：

- failed：命令执行后返回失败；
- blocked：启动、超时、输出上限或环境阻断；
- not_run：明确未执行。

应把事实、原因和限制展示给用户，不能改写为 passed。是否接受带限制的结果由用户在实际结果确认点决定。

## target_merge_in_progress

目标分支仍处于 Git merge。Strixnova 不允许此时强制丢弃 WorkItem。先由 Agent原生完成或 `git merge --abort`，核实主工作树状态后再继续。

## 取消后有工作

选择 preserve、transfer 或 discard。preserve/transfer 只是记录决定，Agent 仍要用 Git 完成实际保留或转交。discard 需要明确破坏性确认，且只丢弃 Strixnova 创建的分支及其工作区内容；额外 worktree 只有在并行模式中存在。

## Python 或测试环境异常

普通使用者先核对安装结果中的 `runtime.python_path` 和 `runtime.entrypoint`，用其中的隔离解释器与命令诊断 Strixnova。业务项目自己的解释器和测试工具由项目配置决定，不必与 Strixnova 共用 `.venv`。缺少 Python 3.12 或 Git 时，由使用者或 Agent 准备前提环境，Strixnova 安装入口只报告缺失项。

只有开发 Strixnova 源码时，才使用本仓库根解释器：

```powershell
.venv\Scripts\python.exe -c "import sys; print(sys.executable)"
```

Strixnova 源码测试只接受仓库根 `.venv`。不要向系统 Python 安装 Strixnova。开发中优先运行受影响测试；最终性能测量按仓库测试说明执行。
