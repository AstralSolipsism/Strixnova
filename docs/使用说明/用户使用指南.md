# 用户使用指南

本轮每项验收、约束和风险都须有明确核验安排；明确留下的延期问题可在后续事项精确承接。Agent 负责整理记录，用户沿用原有确认点作取舍，详见[逐项核验与延期跟进](逐项核验与延期跟进.md)。

首次使用先让 Agent 按[安装与首次使用](installation-and-first-use.md)检查环境并安装 Strixnova。Windows x64、Python 3.12 和 Git 预先准备；离线包提供 Strixnova 和锁定依赖，后续再加载配套 Skill、建立业务项目自己的工程材料。

一个项目首次接入并交付仓库改动时，需要建立产品、领域、架构等基础资料。Agent 负责调查、复用已有材料和起草，你只需决定产品含义与重要取舍；内容按项目规模组织，不要求你填表。后续小改动复用这些资料，只更新受影响部分，按需形成 PRD、SPEC 等阅读产物。

## Strixnova替你承担什么

Strixnova的目标不是让你变成软件工程师，而是让软件工程能力进入建设过程。你负责说清效果和做关键取舍；Coding Agent（智能编码代理）负责调查、形成项目针对性的影响、风险、设计、操作和验证候选；程序负责防止漏掉适用内容、错引用、越过状态和虚假执行结果，但不替任何人判断语义正确。

程序不会根据关键词套话，也不会按文件数量决定项目“有多大”。任何工程理由都应来自 Coding Agent（智能编码代理）对用户确认内容、项目长期政策和真实源码的调查判断。智能编码代理在提交完整评估前必须自检事实依据、项目针对性、范围和遗漏；Strixnova不把同一智能编码代理的第二次输出包装成“独立复审”。

## 你只需要处理三个正常关口

### 方向

确认的是“我们到底在解决什么”，包括目标、范围、非目标、不能破坏的行为、重要取舍和怎样观察成功。方向不清时继续讨论，不进入实施。请求确认前，智能编码代理要主动说明当前理解、确认后形成的方向、产品效果、主要取舍、风险与建议；方向确认只授权继续调查和形成工程方案，不授权修改源码或交付。

最初一句愿望不必已经像需求文档。Coding Agent（智能编码代理）会先把能从项目中查明的事实自己查清，只把真正需要你决定、并且会改变目标或范围的问题拿出来讨论。一次只问一个决定，同时给出推荐答案和它对效果的影响；已经说清的事项不会为了走形式继续追问，也不会要求你回答文件、架构、测试或 DDD（领域驱动设计）术语。

讨论在你与智能编码代理的正常对话中完成，不为每句话建立 Strixnova状态。只在目标、范围、非目标、约束、取舍和验收已经足够明确时形成一份方向卡；还有关键决定没解决时，智能编码代理应明确指出缺口。最终被保存和追溯的是你确认后的方向，不是整段聊天记录。

系统只会在这些内容全部显式出现时提供确认。范围和验收至少各有一项；确实没有的非目标、约束或取舍可以是空清单。方向尚不完整时必须显示具体缺口，不会由程序猜测补齐。

### 完整工程方案

确认的是“按什么办法建设、为什么、会影响什么、怎样验证”。Coding Agent（智能编码代理）要把改前与改后、产品和用户效果、工程逻辑、实施顺序、最高影响风险、验证办法、未知与建议解释清楚。Strixnova会检查十二个稳定影响维度都已被明确分类；真正受影响或未知的维度才需要理由和证据，没有影响的维度只列名称。风险、ADR（架构决定记录）、验证和交付材料只在真实影响或项目规则需要时出现。确认只授权按方案在本地实施和验证，不等于接受最终结果，也不授权 Git 交付、推送或发布。

保障强度不是文档数量。是否需要方案比较、ADR、迁移、运行手册或更广回归，由真实影响决定。

### 实际结果

确认的是“现在真实做成了什么”。Coding Agent 要对照方案说明实际变化、用户可观察效果、验证证据、偏差、失败、阻断、未运行项、限制和建议，而不是只给一个绿色结论。若不符合预期，要求修正即可；代码此时通常还未形成正式结果提交。确认后只授权按项目规则完成本地 Git 交付，不授权远程推送、正式发布或部署。

三个关口都不要求你阅读系统字段、指纹、schema 名或卡片编号。接受或纠正时可以用自己的话说明，无需固定口令或前缀。Agent 结合刚才完整展示的候选判断答复，保留整条原话及判断依据；“可以，但先改……”不会直接接受原候选。如果你说“没看懂”或继续提问，智能编码代理应换一种方式解释同一份候选，流程和版本保持不变。只有会实质改变候选的纠正才进入修订。程序只守住候选身份、版本和流程顺序，不判断说明是否易懂、你是否理解或候选语义是否正确。

## 为什么先测试、后提交

WorkItem 一开始已经有独立 Git 分支；单项建设直接使用主工作树，并行事项才增加外部 worktree。未提交代码不会因对话中断而失去恢复位置，测试也不需要临时 commit。

Agent 在未提交状态完成验证并展示结果；你确认后，Agent 才显式选择本事项文件并形成有意义的原子提交。这样不会在目标分支留下“用户还没确认”的正式结果，也不需要额外的 tree、哈希或凭证系统。

A0 只是同一流程中的最低保障等级，不是 Strixnova 新造的“调查模式”。Coding Agent 平时搜索代码、写临时记录或调用 subagent，不需要交给 Strixnova 管。真正作为事项管理但没有仓库交付的 A0 仍经过三个确认，并完成紧凑的十二维检查；不存在的风险、操作、验证和交付计划可以省略，不创建 Git 工作区、不提交。

验证结果只显示一个明确状态：不需要验证、仍待验证、已经通过、或已经完成但存在问题。失败、受阻和未运行都会原样进入“存在问题”，不会再出现“all_passed=false 但 ready=true”这种需要用户猜意思的组合。

## 多个 WorkItem 怎样并行

已确认方向可以说明事项之间的语义关系：一般关联、属于某个大事项、依赖已有成果、后续延续或替代旧方案。关系由发起关联的事项保存一次；聚焦读取任一方的详情时都能看到，并显示相关事项的当前标题和状态。默认未完成事项列表不展开关系正文，避免把无关理由反复塞给 Agent。

选择关系时依次判断：是不是大事项的一部分，是否必须使用另一事项成果，是否是后续完善，是否取代旧方案；都不是但确实需要追溯时才使用一般关联。关系只是帮助人和 Agent 理解来龙去脉，不会自动改变任一事项的状态或确认。

每项正式实施有自己的 work_ref；需要同时处理时，各并行事项使用外部 worktree：

- 不相交改动分别完成，之后由 Git 正常合入；
- 同一内容发生冲突时由 Git 暴露；
- Agent 解决冲突并重跑受影响验证；
- Strixnova 不建立路径锁、目录锁或语义合并器。

即使声明了“依赖”或“替代”，Strixnova 也不会据此继承测试义务、排期、阻塞实施、检测关系环或处理 Git 冲突。是否推进仍由各事项自身的 CurrentAction 和用户确认决定，内容冲突仍交给 Git 暴露和处理。

目标分支的无关提交不会让其他 WorkItem 全局过期。若新提交真正改变已确认方向或方案，Agent 才重新评估并请你确认。

## 冲突后为什么有时要重新确认

纯行级冲突可能只是在保持原结果。Agent 说明理由，在发生 merge 的目标工作树重跑受影响验证；只有受影响验证全部通过且事后判断无需再测时，才直接完成原生 merge commit，不增加用户确认。若复测失败、受阻、未运行或仍需重测，Agent 必须先重新展示实际限制并请你确认。

如果冲突解决改变你能看到的行为，原“实际结果确认”已经不再对应当前代码。Agent 会在发生冲突的本地目标工作树重新验证、展示和请你确认；确认后才完成 Git merge commit。如果目标或方案也改变，则先回到相应确认点。这不是额外流程，而是旧确认已经失效。

## ADR 和长期项目知识

ADR 不是“一项 WorkItem 一份”。只有会长期影响架构、职责、公共接口、数据、兼容或运行方式的决定才建立 ADR。一份 ADR 可以由多个 WorkItem 分阶段实现；一个 WorkItem 也可以涉及多份 ADR。

项目目标、领域知识、架构原则、工程政策和实现对齐保存在项目正常 Git（版本管理系统）文件中。ProjectEngineeringBaseline（项目工程基线）只定位产品定义、领域模型、目标架构、工程政策和实现对齐的精确修订、当前阶段、代码观察基点和复核状态，不保存正文，也不建立普通长期产物索引。它们会在 WorkItem（建设事项）分支清理后继续存在。Strixnova不维护全部源码能力、符号或调用关系的影子目录。

成熟多语言项目的实现观察不会要求 Strixnova 核心内置每种语言的完整 AST。内置能力不足时，完整工程方案可以精确绑定语言原生分析器；确认的不只是命令名称，还包括可执行文件、入口脚本、配置和支撑文件的实际 SHA-256，运行前会重新核对。准备事实内部按内容分页，Agent 只通过 `alignment inspect` 读取当前有界逻辑页，不需要理解缓存文件；同一源码不得同时归入两个受管作用域。候选写入发现 `prepare` 后有人修改六个目标文件时会停止，不会用旧快照覆盖；写到一半发生进程崩溃时，下次入口会根据持久事务日志恢复一致文件组。

## 软件工程标准怎样进入流程

Strixnova内置版本化治理档案，把权威规范来源映射成工程主题和最小信息要求。普通事项只加载与已识别影响有关的摘要，不把整本标准塞给用户或智能编码代理。

默认结论是“完成 Strixnova内部评估”。机器校验不等于语义正确，智能编码代理自检不等于独立专家审查，内部评估不等于官方合规。如果项目确实需要真人或外部认证，相应状态在真实发生前必须保持为假。

## DDD 等软件工程思维怎样进入流程

软件工程方法先有项目级长期决定，再有具体事项中的使用。ProjectEngineeringPolicy（项目工程政策）明确写出 DDD（领域驱动设计）是已采用、条件采用、未采用还是尚未评估；ProjectEngineeringBaseline（项目工程基线）只定位该政策的精确修订。每个正式项目都独立维护 ProjectDomainModel（项目领域模型）和 ProjectImplementationAlignment（项目实现对齐），方法采用状态不决定它们是否存在。

大型项目可以把领域资料自由组织成“卷、篇、章、专题”并任意嵌套。目录名称不会被程序擅自解释成子域或限界上下文；只有需要正式引用和追溯的领域事实才获得稳定 Fact（事实）身份。智能编码代理先看轻量目录，再按当前事项读取必要正文，不需要把全部资料一次塞进上下文。

“项目已采用 DDD（领域驱动设计）”只说明项目选择用这套方法管理领域知识，不表示所有领域事实都已经写进代码。项目实现对齐会完整记录行为文件归属、实际依赖、目标责任、偏离和未知，并由目标责任推导领域事实实现程度。未实现项可以诚实保持没有代码路径，部分实现或已实现项必须引用真实代码、架构模块和验证证据；覆盖数字不等于语义正确或外部认证。

实施过程中，Coding Agent 可以直接使用安装后的 `strixnova alignment` 入口，把已确认方案中的观察范围应用到实际代码。Rust、Go、TypeScript 等可先用内置静态观察，C#、C++ 或其他语言需要更深构建语义时，只有工程方案已经确认精确工具计划且本次明确授权才会执行。工具不可用、部分覆盖或失败不会阻止继续阅读代码、领域资料并与你讨论，但系统会把缺口留在草稿中，不能宣称已经完整对齐。程序只填充路径、散列、关系和回执，归属、架构含义和责任完成度仍由 Coding Agent 结合项目事实判断，最终候选仍要随实际结果交给你确认。

单个 WorkItem（建设事项）影响领域、架构、接口或数据时，Coding Agent（智能编码代理）再根据项目工程政策和当前事实形成“本事项应用哪些 DDD（领域驱动设计）技术，或为什么考虑后不应用”的候选。这个判断随完整工程方案一起确认，不增加第四个用户关口，也不要求你理解或单独确认方法名。

程序不会看到“领域”两个字就机械启用 DDD，也不会把文件夹直接当成限界上下文。采用 DDD 不会自动提高保障等级、重排代码目录、生成合规分数或宣称外部认证。最后的实际结果还要逐项说明计划的方法是否真的落实；没落实就必须显示偏差和限制。

## Strixnova 会不会拖累 Agent

默认不会把整个 WorkItem、历史或所有工程字段反复塞入上下文。轻量 Skill 先让 Agent 读取最小 CurrentAction，只在当前动作需要时再取方向、评估、方案、回执或 Git 事实中的一项。写入后直接使用返回的新下一步，不重复查询。

事项完成后仍可按需查看两种工程追溯：`current` 只回答“哪些关系已经随本地合入成为当前事实”，`audit` 还回答“过去计划过、取消过或被替代过什么”。它们不会出现在默认列表中，也不会建立第二份历史账本。

Strixnova 不管理 Agent 的搜索过程、读取文件数量、prompt、会话或 subagent。Agent 可以自主使用 subagent 做调查或交叉检查，但这只是 Agent 的内部能力，不会被 Strixnova 伪称为独立复审证据。

## 取消事项

没有未合入工作时可以直接取消。有脏文件或未合入提交时，Strixnova 会让你选择：

- preserve：保留当前分支和现有工作区；
- transfer：明确记录转交去向，由 Agent 使用 Git 完成；
- discard：明确确认后丢弃 Strixnova 创建的分支及其工作区内容。

Strixnova 不自动 stash、覆盖、删除非自己创建的分支，也不会在 Git merge 尚未处理时强行清理。

## 哪些事情仍由你管理

- 是否把本地提交推到远程；
- 远程分支、代码评审、CI/CD 和发布平台；
- 需要真实组织权限、硬件、真人审查或外部认证的环节；
- 是否接受项目治理档案的长期裁剪。

Strixnova 会记录这些环节是否完成或成为限制，但不会伪装成它已经替你完成。
