# 逐项核验与延期跟进

核验安排回答“本轮每个要求怎样检查”，延期跟进回答“明确留下的问题以后由谁处理”。内容由 Agent 整理，用户仍在现有方向、方案和实际结果确认点判断取舍。

## 本轮要求逐项有交代

Agent 从当前方向的验收、约束和本轮风险整理目标。已有测试命令的 covers 直接形成安排，一条命令可以覆盖多项；其他目标明确选择 Agent 审阅、复用已有证据或保留未核验，并说明依据与后果。缺项会在方案确认前被指出。

交付时分别展示命令证据和 Agent 审阅结论。命令全部通过只说明已计划命令的执行结果，不代表所有业务含义已被机器证明。明确未核验不能改称满足；若需放宽原验收要求，通过既有修订与确认路径处理。

程序只检查引用、版本、条目完整性和真实回执。文档语义可以由 Agent 对照已确认规则审阅，无需为了形式完整生成测试命令。旧方案显示“未按新机制逐项核对”，不自动补为通过。

## 明确留下的问题怎样承接

当前范围的问题在本轮修复。用户接受并结束跟进的限制留下决定即可；承诺以后处理的条目则说明责任、日期或复查条件、完成标准。普通的证据适用范围说明不自动创建任务。

无需先建立后续事项，即可查询已接受的延期承诺：

```text
strixnova status --project-dir <项目目录> --follow-ups
strixnova status --project-dir <项目目录> --follow-ups --include-closed
strixnova status --project-dir <项目目录> --follow-ups --limit 25 --cursor <上一页返回的引用>
```

本入口独立于 Git 权威采用；不写数据库、不初始化事项。日期以本机日期提示到期，业务条件由 Agent 调查判断。返回只包含明确记录且已接受的承诺，不从旧历史文字猜测技术债。

后续事项明确承接时，Agent 在方向的 follows_up 关系中复制查询返回的精确 follow_up_ref，避免只关联到整个旧事项。处理完成后逐项说明已解决、部分解决、继续开放或接受限制；原问题只在后续实际结果被接受后更新处置。取消一个后续事项不会自动取消原承诺。

其他结果已推进同一条目时，过期处置会被拒绝。Agent 重新读取当前版本和依据，按原有纠正或重规划路径更新候选并展示，不能覆盖新决定。原记录保持不变，查询汇总后来接受的结果。

详细字段与示例位于同版随包 Skill 的 engineering-assessment、delivery 和 follow-ups 参考资料。用户无需手工填写这些字段。
