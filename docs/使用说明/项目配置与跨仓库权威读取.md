# 项目配置与跨仓库权威读取

当前源码使用 `strixnova.project-config.v1` 定位项目、成员仓库和工程基线，使用基线 v1 引用各仓库中的长期权威及代码版本组合。一个项目保留一份声明、一份基线及每类权威；它们可以位于不同成员仓库。

当前源码接通配置、权威读取、多仓库整体方案、实施、内容组合验证、实际结果接受与逐仓库交付。执行用法见[多仓库事项与整体方案](多仓库事项与整体方案.md)，候选验证范围见[当前验证状态](../engineering/validation-status.md)。本文不证明当前宿主已安装对应程序。

## 1. 版本化项目声明

配置保存在某个成员仓库的 `strixnova-project.yaml`。无需专门建立治理仓库。先读取当前完整合同：

```powershell
strixnova context contract configuration
strixnova context contract bindings
```

以下示例的身份须替换为项目实际身份；已经分配的仓库身份不因检出目录变化而重建。

```yaml
schema_version: strixnova.project-config.v1
project_id: PROJECT-1111111111111111
repository_id: REPO-1111111111111111
repositories:
  - repository_id: REPO-1111111111111111
    owner_project_id: PROJECT-1111111111111111
    purpose: 前端与项目声明
  - repository_id: REPO-2222222222222222
    owner_project_id: PROJECT-1111111111111111
    purpose: 后端与部分工程材料
engineering_baseline:
  repository_id: REPO-1111111111111111
  path: docs/engineering/baseline.yaml
  ref: null
default_integration_ref: main
```

顶层 `repository_id` 标识配置所在仓库。`default_integration_ref` 只选择该仓库的本地集成版本，不表示其他仓库也读取同名分支。外部依赖仓库使用可选的 `external_repositories`，其归属项目须不同，不能用作本项目的基线或长期权威承载仓库。

## 2. 明确本机绑定

当 `--project-dir` 就是配置仓库根时，程序可以只绑定这个明确入口；其他成员分别显示为未绑定。需要从非 Git 入口读取，或绑定分离仓库时，通过 `--project-bindings` 提供 JSON 文件。

假设目录如下：

```text
workspace/
  project-entry/
    bindings.json
  frontend/
    strixnova-project.yaml
  backend/
```

`bindings.json` 的内容：

```json
{
  "schema_version": "strixnova.project-bindings.v1",
  "project_id": "PROJECT-1111111111111111",
  "configuration": {"repository_id": "REPO-1111111111111111"},
  "management_root": "state",
  "repositories": [
    {"repository_id": "REPO-1111111111111111", "path": "../frontend"},
    {"repository_id": "REPO-2222222222222222", "path": "../backend"}
  ]
}
```

所有本机相对路径相对于 `--project-dir`，不是相对于 JSON 文件所在目录。`configuration.path` 可明确选择配置仓库内的其他普通相对路径，省略时使用 `strixnova-project.yaml`。绑定中的项目和配置仓库身份必须与声明相符，不能用绑定隐式新增成员。

在 workspace 目录执行：

```powershell
strixnova --project-bindings .\project-entry\bindings.json status --project-dir .\project-entry
```

读取不会创建 state 目录、事项数据库或分支。未绑定的无关代码仓库不阻塞读取；基线及本次需要的权威所在仓库不可用时，会明确拒绝相应读取。

## 3. 基线中的仓库与版本

基线使用 `strixnova.project-engineering-baseline.v1`。每个 `authority_refs` 记录具有 `repository_id`，保留原路径、权威身份、修订及采用状态；可用 `ref` 指定精确 Git 提交。`code_version.repositories` 分别记录仓库的代码版本。完整结构见[基线 v1 Schema](../../strixnova/src/strixnova/resources/project-engineering-baseline-v1.schema.json)。

以下只展示一个引用片段；示例提交必须替换为该后端仓库中真实存在的精确提交：

```yaml
authority_refs:
  product_definition:
    repository_id: REPO-2222222222222222
    path: docs/product/definition.yaml
    ref: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    product_id: PRODUCT-1111111111111111
    revision_id: REVISION-1111111111111111
    status: {revision_status: confirmed, adoption_status: current}
```

版本选择规则同样适用于配置中的 `engineering_baseline`：

- 同仓库引用省略 `ref` 或使用 null 时，继承包含它的读取版本。这样不需要让一个提交在自身内容中预先引用自己的提交号。
- 从不可变内容跨到另一仓库时，必须给出精确提交。缺少时返回 `cross_repository_commit_required`，不读取另一个仓库的最新分支。
- `status --at-commit` 选择的是配置仓库版本，其余版本由该配置和基线中的引用确定。
- `status --working-tree` 明确读取候选组合；未固定的引用读取工作树，固定引用仍保留指定版本。各材料的实际来源单独返回，候选检查不表示采用或完整验证通过。

每类权威内部的 Collection、Source、从属底账等路径，继续在该权威所属仓库与版本内解释。实现对齐通过已选领域和架构读取器取得上游材料，不在自身仓库猜找同名文件。

## 4. 如何解释结果

`configuration_content_ref`、`baseline_content_ref` 和 `authority_content_refs` 分别说明声明、基线及各权威的仓库、路径和实际提交。`observed_commit` 对应基线读取版本，应结合 `observed_repository_id` 使用，不能解释为整个项目共用的 Git 提交。

读取成功不证明多仓库代码观察、验证内容组合或整体阶段完成。每项结论仍须核对其原始回执和适用输入；既有工程保障投影和观察不因入口可读而自动更新。

事项可使用分离的管理位置和明确绑定的成员仓库。程序按已接受方案建立各仓库执行上下文，组合实际结果并整体接受后，再逐仓库交付。取消和重新规划保留原先已发生的交付事实；路径、成员归属和必要版本无法确认时，相应操作在副作用前阻断。详见[多仓库事项与整体方案](多仓库事项与整体方案.md)。
