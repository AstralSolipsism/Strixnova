# 完成归属与轻量收尾合同

> 适用版本：Strixnova 0.1.0.dev0
> 核心原则：先在未提交工作树中验证和确认，之后才由智能编码代理形成原子提交并本地合入。

纯调查、讨论或非交付原型不属于正式实施：当已确认方案明确 `formal_implementation=false` 且没有仓库操作时，不建立 Git 工作区。它可以在项目根运行明确选择的本地检查，展示真实结果并经用户确认后直接完成；零计划命令时不得制造虚假回执。

## 1. Git 是实施边界

正式实施要求项目根就是本地 Git（版本管理系统）仓库。一个 WorkItem（建设事项）记录：

- target_ref：最终合入的本地目标分支；
- base_commit：开始实施时 target_ref 的提交；
- work_ref：Strixnova 创建的 `strixnova/<work-item-id>` 本地分支；
- worktree_path 与 worktree_mode：单项建设为主工作树 `in_place`；并行事项为仓库外 `linked` 工作树；
- result_commits：用户确认实际结果后由 Agent 形成的一个或多个提交；
- integrated_commit：合入 target_ref 后的本地提交。

这些都是 Git（版本管理系统）事实引用，不是第二套源代码快照。Strixnova不保存全仓文件清单、逐路径前置哈希或测试树身份。

## 2. 开始实施

只有完整工程方案确认后才能建立工作区。单项建设要求主工作树干净并检出 `target_ref`（目标引用）；发现已有改动时停止，让用户或智能编码代理先明确归属，不自动暂存。主工作树正承载另一事项时，新并行事项使用显式的仓库外工作树。

Strixnova从当前 `target_ref`（目标引用）精确记录 `base_commit`（基线提交）并创建自己命名的本地分支；单项建设直接切换主工作树，并行时才增加外部工作树。当前产品不建立代理运行领域对象，不保存、认证或管理代理会话；调用来源只作为请求事实，不能决定写权。多个并行 WorkItem（建设事项）可以从各自基线提交在不同工作树实施。

## 3. 实施与本地验证

Coding Agent（智能编码代理）自主选择阅读、搜索和编辑工具。Strixnova不限制工具种类和读取规模。

VerificationRunner（验证执行器）只运行工程评估中已经明确选择并进入确认方案的命令。执行回执记录实际参数、工作目录、开始时间、时长、退出码、受控输出摘要、本地原始输出引用、证明范围、结果和限制。命令结束后，智能编码代理查看普通 Git（版本管理系统）差异，再单独提交代码变化与是否需要重测的工程判断；程序不把运行前预测写成事后事实。

结果为：

- passed：命令实际成功；
- failed：命令实际运行且失败；
- blocked：命令启动、超时或环境条件阻断；
- not_run：明确没有运行并给出原因。

`failed`（失败）、`blocked`（受阻）和 `not_run`（未运行）可以如实展示给用户，但不能隐藏成“全部通过”。缺失命令回执或明确要求重测时，不能形成 ActualResult（实际结果）。

## 4. ActualResult 与确认

ActualResult（实际结果）由智能编码代理根据实际文件和最新验证回执编写，包含效果摘要、已交付结果、偏差、限制、每项命令最新回执身份，以及本事项实际建立、更新、实现或删除的长期工程文件。未发生变化的文件不伪装成本事项产物，其证据直接引用工程评估中的可重读来源或实际交付结果。

凡工程评估中 `method_applications.decision=applied` 的 planned use，ActualResult 必须逐项给出 `realized` 或 `not_realized`、具体效果和真实证据引用。`not_realized` 必须同时进入方法偏差及用户可见限制；`considered_not_applied` 不生成虚假结果。这个结果只证明已计划的方法技术在本事项中的落实情况，不把 DDD 标签升级为整个项目实现已完全对齐或外部合规。

用户确认时允许 worktree 仍有未提交改动。Strixnova 不要求测试提交，也不把回执加密绑定到文件字节、Git tree 或临时 commit。验证后代码变化时，Agent 查看普通 diff 并重跑受影响验证。

请求实际结果确认前，智能编码代理必须把已确认方案与真实实施对照说明，讲清修改前后、用户可观察效果、验证、偏差、风险、限制、建议以及授权边界。实际结果确认只接受这次展示的实施与验证事实，并授权后续精确本地 Git 提交、合入和清理；不授权远程推送、正式发布或部署。用户可以自然表达明确接受或具体纠正，Agent 保留原文、显式决定及依据；程序核对精确绑定，用户不必复制候选指纹、决定标签、版本、Schema 名称或结果卡编号。用户表示看不懂或继续提问时，重述同一个 ActualResult 并保持确认待定；只有实质纠正才回到实施、验证和重新展示。

用户拒绝实际结果时回到实施；修正、验证和展示后重新确认。

## 5. 提交、合入和清理

实际结果确认后：

1. 智能编码代理只显式暂存本事项文件，不使用无边界全量暂存；
2. 智能编码代理编写有意义的一个或多个原子提交；
3. Strixnova检查工作树干净、基线提交仍是事项分支祖先并记录结果提交；
4. 按项目政策本地合入目标引用；缺省采用非快进合入，也支持项目选择仅快进合入；
5. 合入成功后记录本地集成提交；
6. 只有工作区干净、提交已合入、分支确由 Strixnova创建时，才删除事项分支；并行时由 Strixnova创建的额外工作树一并删除；
7. 清理成功后 WorkItem（建设事项）才是 `completed`（已完成）。

Strixnova不执行变基或压缩提交，不调用远程推送、拉取或抓取，不创建远程分支。远程同步完全由用户管理。

## 6. Git 冲突

Git（版本管理系统）是唯一内容冲突判定者。合入产生冲突时，Strixnova记录原生冲突并停止，不建立路径锁或语义合并器。

智能编码代理解决后必须明确提交两个判断及理由：

- 是否改变用户可见结果；
- 是否改变已确认方向或工程方案。

如果两者都不变，智能编码代理必须明确列出受冲突影响的重测命令标识，并在发生合并的本地目标工作树逐项重跑。每个命令都必须有冲突判断之后形成的最新回执和事后代码变化判断，且明确无需再次重测；全部通过时才可由智能编码代理完成原生合并提交而不新增用户确认。失败、受阻或未运行必须重新展示实际限制并由用户确认，不能靠无关回执或回执数量解锁。Strixnova随后只核验集成事实，不再次执行合并。

如果用户可见结果改变，原 ActualResult（实际结果）和确认失效。冲突解决此时已经存在于发生原生合并的本地目标工作树：智能编码代理必须在那里运行受影响验证、重新形成 ActualResult（实际结果）并请用户确认；确认后才由智能编码代理完成原生合并提交。Strixnova不把冲突内容复制回 WorkItem（建设事项）分支，也不建立第二套合并。

若方向或方案也改变，则保留原评估身份、增加评估修订并进入相应方案确认；新评估和新确认完成后，仍在目标工作树验证当前冲突解决。任何重新确认之前，智能编码代理都不得完成合并提交。若用户不接受新方向、方案或结果，智能编码代理使用原生 Git（版本管理系统）中止或继续修正该合并，Strixnova不替用户选择。

## 7. 取消与失败

取消前程序读取原生 Git（版本管理系统）状态，不接受调用方自行声称“没有工作”。

- 没有脏文件和未合入提交时可直接取消；
- 有未合入工作时进入待处理状态，用户选择 preserve、transfer 或 discard；
- discard 是破坏性动作，必须明确确认；
- 目标分支仍在原生合并中时不得强制丢弃 WorkItem（建设事项），先由智能编码代理解决或中止合并；
- 程序不自动暂存、覆盖、恢复或删除非 Strixnova创建的分支。

`preserve`（保留）和 `transfer`（转移）只记录用户决定及去向，不假装内容已经被程序移动。具体保留或转移由智能编码代理使用 Git（版本管理系统）完成并核实。

## 8. 长期工程文件

ProjectProductDefinition（项目产品定义）、ProjectDomainModel（项目领域模型）、ProjectArchitectureDescription（项目架构描述）、ProjectEngineeringPolicy（项目工程政策）、ProjectImplementationAlignment（项目实现对齐）、ADR（架构决定记录）和接口文件都随源码进入 Git（版本管理系统），但职责彼此独立。ProjectEngineeringBaseline（项目工程基线）只定位这些权威的精确修订、独立采用状态、当前架构阶段、代码观察基点和待复核状态，不保存任何权威正文或长期产物索引。

工程评估的 operation（产物操作）对普通长期工程文件明确声明产物身份、类型、路径和操作；ActualResult（实际结果）必须完整交代每个已计划发生变化的长期文件，不把未改动文件伪装成本次产物。未改动证据直接引用工程评估中的可重读来源或实际交付结果；创建、更新或移动后的文件必须真实存在并通过自身合同校验，删除项必须真实不存在。长期权威的当前采用身份由项目工程基线的精确引用表达，普通产物不反向进入基线形成混合索引。ADR（架构决定记录）的决定状态与实现状态分别维护；WorkItem（建设事项）分支清理不删除已经合入目标分支的架构决定记录。

领域变化另外使用带 `observed_commit` 的 Fact 引用、计划的 Fact 变化和实现对齐变化表达，不把每个 Fact 伪装成 ProjectEngineeringBaseline artifact。ActualResult 必须逐项闭合这些计划；声明 `realized` 时，程序从调查 Git commit 与实施工作树重新读取独立领域模型和实现对齐，核验当前 Fact、tombstone、lineage、Source 位置和 alignment 身份与计划一致，并拒绝同一 Source 内未计划的 Fact 或对齐记录变化。首次整体采用领域模型由采用变化和长期权威覆盖，不要求逐项枚举模型原有全部 Fact。程序只证明结构、前后变化和引用事实，不证明领域语义正确。

用户看到 ActualResult（实际结果）之前，所有声明为本次建立或更新的长期权威必须通过各自合同校验。新项目的产品定义、领域模型、目标架构和工程政策必须先分别展示精确候选并由项目负责人独立接受、由项目工程基线采用，实施后再逐类报告五类权威及新实现对齐候选；程序随后从项目配置、项目工程基线和五类权威重新校验整条引用链。普通实际结果接受只能授权程序机械定档本轮精确实现对齐，不能确认上游长期权威。ADR（架构决定记录）必须通过身份、状态、元数据头、非空正文及其声明关系的一致性校验；若项目明确声明了 ADR（架构决定记录）模板或章节约定，再按项目约定检查。正文的工程质量由 Coding Agent（智能编码代理）在评估和实施中形成候选，并在对应方案、独立长期权威或实际结果入口交由项目负责人决定；程序不写死中文标题，也不由格式反推决定内容专业正确。
