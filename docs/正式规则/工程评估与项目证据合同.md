# 工程评估与项目证据合同

> 适用版本：Strixnova 0.1.0.dev0
> 核心原则：Coding Agent（智能编码代理）调查并形成工程语义候选，项目负责人确认适用的正式决定；程序只校验结构、真实引用、关系、版本和确定性规则，绝不生成或裁决语义。

## 1. 输入顺序

方向确认后，工程语义链固定为：

1. Coding Agent（智能编码代理）自主选择工具调查源码、ProjectEngineeringPolicy（项目工程政策）和 ProjectEngineeringBaseline（项目工程基线）定位的精确长期权威；
2. Coding Agent（智能编码代理）形成一份完整 `strixnova.engineering-assessment.v1`（Strixnova 工程评估），提交前自检事实依据、项目针对性、范围一致性、遗漏和空泛内容；
3. 若现行产品、领域、目标架构或实现对齐准备改变，在同一评估中形成 AuthorityChangeSet（权威变更集），说明旧基线、具体变化和全部下游处置；
4. Coding Agent（智能编码代理）形成 SemanticReview（语义复核），从八个固定角度检查产品、领域、架构、方案、场景、风险和证据是否表达同一建设意图；
5. 把全部操作和验证拆入有明确依赖关系的 ImplementationSlice（实施切片），再用 OwnerView（负责人视图）把同一方案改写成负责人容易决策的阅读顺序；
6. 程序校验字段、SourceReference（来源引用）、权威基线、引用覆盖、切片依赖、操作冲突、路径、命令格式和项目已声明规则；它不判断语义复核的文字或建议是否正确；
7. 程序从通过校验的同一评估投影 `strixnova.engineering-plan.v1`（Strixnova 工程方案），保留经规范化去重后的验证命令、实现观察 provider 计划及其确定性 ID（标识），不复制或改写工程语义；
8. 用户一次性确认完整工程方案。

SemanticReview（语义复核）是同一 EngineeringAssessment（工程评估）中的智能编码代理检查记录，不是 Strixnova管理的第二套复审流程。程序不会重新调用或管理另一个智能编码代理，也不会把同一代理的自检伪称为真人、独立审查或机器语义证明。智能编码代理可以自主使用子代理或其他手段交叉检查，但 Strixnova只保存它提交的结论和真实证据边界。

程序不得补写缺失的目标、理由、风险、设计、操作、验证命令、阶段或通过结论。

方向确认的输入是 `strixnova.direction-decision.v1`。六组方向语义仍为 `goal`、`scope`、`non_goals`、`constraints`、`tradeoffs` 和 `acceptance`；另有必需的 `decision_context`（决定上下文绑定），可选 `work_item_relations` 用于声明已经有真实目标事项的跨 WorkItem 追溯关系。`scope` 与 `acceptance` 至少各一项；其余方向语义数组可诚实为空，但字段不能省略。尚未达到这个合同的内容只能作为讨论草稿，并同时指出 blockers，不能被程序修成可确认方向。

`decision_context` 不是第二份产品定义，也不是程序生成的需求。对于已有已采用产品权威的项目，它必须包含：当前 `context_ref`（产品修订引用）、至少一个由 Coding Agent（智能编码代理）判断与本事项相关的 `capability_refs`、对当前产品定义全部 `non_goals` 和 `constraints` 各恰好一次的 `guardrail_dispositions`，以及诚实的 `assumptions`。每项护栏处置由 `decision_ref`、`disposition=applies|not_applicable|reconsider` 和非空 `reason` 组成；每项假设给出 `statement` 和 `reconsider_when`。对于尚未建立产品权威的新项目，`context_ref` 必须为 null，能力和护栏处置必须为空，方向只承接用户愿望并在后续 create_project（创建项目）评估中建立长期权威。

程序只读提供当前产品目的、能力目录以及全部非目标和约束，并校验上下文版本、引用存在、唯一性、完整覆盖和失效关系。哪些能力相关、每条护栏为何适用或不适用、假设是否合理，全部由 Coding Agent（智能编码代理）基于用户原话和项目调查形成，程序不得使用关键词、路径或固定规则生成或评价这些判断。`reconsider` 表示当前方向建议修订既有产品护栏，不表示护栏已经失效；工程评估必须明确把 `product_scope` 判为 affected 或 unknown，并规划对应产品定义候选，在新产品修订独立确认前仍按旧护栏约束实施。产品修订或护栏集合变化后，旧方向不得继续进入工程评估、实施或实际结果接受；CurrentAction（当前动作）必须基于精确版本、引用和覆盖把下一步投影为修订方向，保留仍有依据的既有决定，并经原方向确认点重新确认，不新增普通用户关口。

该结构合同不表示把用户第一句话直接转成字段。提交前，Coding Agent（智能编码代理）必须先读取程序提供的完整当前决定上下文，再自行查明可发现的项目事实；它不能因为用户只提出模糊方向就让程序猜相关需求，也不能把完整产品正文倾倒给用户。智能编码代理先形成逐项有理由的判断，只向用户澄清会改变六组方向事实、既有护栏或重大假设的未决决定；一次讨论一个决定，并给出推荐答案和用户可见影响。明确请求不得为了填流程继续追问，达到安全确认条件后也不得无界调查。澄清对话不形成新的 Strixnova权威，只有最终 DirectionDecision（方向决定）进入现有方向确认点。

用户对澄清问题、推荐方案或业务取舍的回答只解决该未决决定，不确认随后才形成的完整方向。方向、工程方案和实际结果进入确认前，智能编码代理必须依据当前完整候选主动说明现在或修改前的状态、接受后的变化、产品和用户效果、工程逻辑、主要影响与风险、未知、推荐以及本次授权边界；篇幅按真实复杂度组织，不套固定标题。形成、提交或展示候选的同一轮不得代签确认。用户表示看不懂或继续提问时，只换一种方式解释同一候选并保持确认待定，不调用确认、不增加版本；只有实质纠正才退回并修订。

三个普通确认关口允许用户自然表达明确接受或具体纠正。候选正文、WorkItem 身份、当前版本、决定标签和内容指纹由程序绑定，Agent 从同一 CurrentAction 带入；用户不必阅读或复制这些字段。Agent 保留用户逐字原文，提交显式接受或要求修改的决定及依据，模糊回复、沉默和问题保持待定。程序只验证声明结构、引用、版本和指纹，不解释用户自然语言、不证明用户理解。

### 1.1 引导式形成与三个独立裁剪轴

GuidedFormation（引导式形成）是贯穿产品与领域候选、建设事项方向、工程方案和结果纠偏的既有原则。Coding Agent（智能编码代理）先调查用户已经表达的意图、当前长期权威、项目资料、代码和环境事实，只逐步解决会实质改变结果的缺口；项目负责人可以随时纠正，候选已经足以下游在不发明关键决定的情况下继续时必须停止追问。它不建立新的持久化对象、工作模式、状态机、确认点或命令入口。

形成下一步建议时，智能编码代理必须分别判断并说明三个互不替代的裁剪轴：

| 裁剪轴 | 判断问题 | 主要依据 | 现有承载 |
|---|---|---|---|
| 需求形成深度 | 下游是否仍需猜测客户、问题、边界、关键取舍或成功判断？ | 用户意图、已确认权威、项目调查和仍未解决的决定 | 正常对话、长期权威候选或 DirectionDecision（方向决定）候选 |
| DeliverySpan（交付跨度） | 最少需要几个可以分别获得价值并独立验收的结果？ | 独立价值、共享决定、先后依赖和跨单元协调范围 | 一个 WorkItem、多个有真实关系的 WorkItem，或项目级建设建议 |
| 保障深度 | 每个可交付结果需要多深的调查、审查和验证？ | 真实影响、风险、可逆性、不确定性和项目工程政策 | EngineeringAssessment（工程评估）与 AssuranceBand（保障等级） |

三个轴必须各自给出项目特定理由。单个文件的不可逆数据变化仍可能是“一个 WorkItem + 高保障”，大量机械且易恢复的文件改动也不自动成为高保障事项。关键词、文件数量、代码行数、预计会话数、活动名称和产物名称只能作为调查线索；程序不得用这些信号生成形成路线、拆分事项或选择保障等级，只校验智能编码代理写入现有合同的明确声明、引用和政策下限。

目标、范围、产品护栏和验收已经足够明确时，智能编码代理使用快速起草节奏，调查后直接形成现有候选；客户、问题、边界、关键取舍或成功判断仍不清楚时，才逐项辅导。两种节奏使用同一 DirectionDecision、长期权威和确认合同，不要求用户预选模式，不增加状态或确认次数。

DeliverySpan（交付跨度）按可验收结果判断，而不是按内部步骤或风险高低判断：一个可以独立接受的结果形成一个 WorkItem；多个能分别交付和接受、但共享上层目标的结果形成多个 WorkItem，并只在真实关系已经明确时使用 WorkItemRelation；涉及多个长期产品或跨单元架构决定、且这些决定尚未定档时，先形成项目级长期权威候选。ImplementationSlice（实施切片）只拆分一个 WorkItem 内部的实施顺序，不能冒充另一个用户价值或 Story（故事）。现有关系只用于追溯，不提供 Epic（史诗）聚合接受、进度汇总或智能编码代理调度。

常见软件工程产物名称按以下方式映射，不能取得平行写权：

| 形成方式或阅读名称 | 唯一正式承载 | 边界 |
|---|---|---|
| Product Brief（产品简述）、PRFAQ（新闻稿与常见问题） | ProjectProductDefinition（项目产品定义）与 ProjectDomainModel（项目领域模型）候选 | 只提供可选的思考顺序；需要长期保存的事实进入对应权威 |
| PRD（产品需求文档） | 产品定义、领域模型及必要架构决定的组合阅读投影 | 必须绑定精确修订；修改含义要先修订来源权威 |
| SPEC（规格） | DirectionDecision 及相关 EngineeringPlan（工程方案）的阅读投影 | 不建立独立状态、确认或可编辑真相 |
| Architecture Spine（架构骨架） | ProjectArchitectureDescription（项目目标架构描述）或 ADR（架构决策记录）候选 | 只保留跨单元且存在真实取舍的决定；局部可逆选择留在工程方案 |
| Story（故事） | 一个可独立验收的 WorkItem 候选 | 不等同于 WorkItem 内的 ImplementationSlice |
| Epic（史诗）、Initiative（项目倡议） | 当前不建立一等领域对象 | 多事项用现有关系表达已知追溯，不声称具有聚合与调度能力 |

SDD（规格驱动开发）的部分形成步骤可以由随包 Skill（技能）作为 ArtifactFormationGuide（产物形成指引）提供，但使用该指引只表示智能编码代理采用了写作与检查帮助，不表示受管项目已经采用某种 EngineeringMethod（工程方法）。项目方法采用仍必须由 ProjectEngineeringPolicy（项目工程政策）按该项目真实需要单独记录。

规划或实施发现已确认产品、领域或目标架构语义错误时，必须回到对应长期权威形成精确修订候选，并用 AuthorityChangeSet（权威变更集）处置全部下游影响。不得只改 PRD、SPEC、Story、OwnerView、实施计划或其他阅读投影来宣称上游事实已经变化。

### 1.2 WorkItemRelation 本地关系档案

关系只在源 WorkItem 的已确认方向中保存一次。读模型使用 `declared` 表示由当前事项声明的关系，使用 `referenced_by` 表示其他事项指向当前事项；这两个名称表示事实归属，不是执行流或依赖调度。

| 存储类型 | 源 WorkItem 的含义 | 目标 WorkItem 的含义 |
|---|---|---|
| `related_to` | 与目标有无法用更具体类型表达的一般关联 | 两者互相关联 |
| `part_of` | 是目标大事项的一部分 | 目标包含该子事项 |
| `depends_on` | 需要目标事项已经形成的成果 | 被源事项依赖 |
| `follows_up` | 是目标事项之后的延续或完善 | 后面产生了该延续事项 |
| `supersedes` | 当前方向或方案取代目标事项的旧方向或方案 | 被当前事项取代 |

`related_to` 只是兜底；能使用更具体类型时不使用它。概念对照来源是 [DCMI Metadata Terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/) 中的 `relation`、`isPartOf/hasPart`、`requires/isRequiredBy`、`replaces/isReplacedBy`，以及 [OASIS OSLC Change Management 3.0 Vocabulary](https://docs.oasis-open.org/oslc-domains/cm/v3.0/cs02/part2-change-mgt-vocab/cm-v3.0-cs02-part2-change-mgt-vocab.html) 中的宽松 `relatedChangeRequest` 和父子关系。`follows_up` 是 Strixnova 本地扩展；这些来源只帮助约束自然含义，不据此宣称 Strixnova 实现了对应 RDF 模型、OSLC 服务或外部标准合规。

每条关系的项目理由由 Coding Agent（智能编码代理）根据用户和项目事实形成，程序只校验字段、类型、目标存在、自关联和精确重复，不生成理由、不判断循环，也不推导调度、阻塞、测试义务、锁、合并或冲突处理。

## 2. EngineeringAssessment

工程评估直接保存以下工程语义，不再套一层通用 information-item 容器：

- `assessment_id` 与单调递增的 `assessment_revision`；
- `direction_ref={work_item_id,direction_version}`，精确引用当前已确认方向；
- 调查时项目状态 `investigation_ref`；
- `change_context`；
- 有限 `source_references`；
- 十二维 `impact_scope`；
- `risk_assessments`、`alternatives_and_tradeoffs`、`design_decisions`；
- `operations`、`adr_plans`、`verification_commands`；
- 实现观察确需语言或构建工具补充时的 `external_observation_provider_plans`：逐范围绑定 provider 身份与版本、完整 argv、源码 glob、用途专属进程政策和有限资源上限；
- 现行核心权威发生变化时的 `authority_change_set`（权威变更集）；
- 产品、领域或架构受影响时的 `semantic_review`（语义复核）；
- 正式实施的 `implementation_slices`（实施切片），让每项操作和验证只属于一个有顺序的小步；
- 面向项目负责人的 `owner_view`（负责人视图）：决策支持必须说明当前问题、为什么重要、影响、推荐、替代选择、不处理后果、下一步和最多五个必要问题；工程上下文保留产品与领域变化、架构责任、实施顺序、风险、验证和未知；
- 无命令时的 `verification_not_required_reason`；
- `delivery_plan`、`unknowns_and_limitations`、`requested_assurance`。

目标、范围、非目标、约束、取舍和验收只保存在已经确认的 DirectionDecision 中。工程评估引用该方向版本，不得再复制改写一份 requirements、acceptance 或 constraints。方向变化时必须重新经过方向确认；只有工程事实或方案变化时才增加 assessment_revision。

除身份、方向引用、ChangeContext、ImpactScope 和 requested_assurance 外，其余工程章节只在存在真实内容时提交；缺省数组由程序规范化为空数组，`delivery_plan` 在不适用时为 null。结构缺省不代表程序生成了风险、设计、操作或结论。

正式评估的 `investigation_ref`（调查版本引用）必须由程序解析并保存为不可变 Git commit（版本管理提交）。它只表示本轮调查采用的项目状态，不是文件快照或散列协议。程序从该提交确定性定位和校验项目配置及项目工程基线，智能编码代理不必把这两个绑定重复声明为 SourceReference（来源引用）；只有具体语义主张实际使用某份正文时才提交来源引用。新项目即使只有空初始提交也可使用该身份。

`operations`（产物操作）使用 `create`（新建）、`modify`（修改）、`delete`（删除）或 `move`（移动），记录仓库相对路径、理由、证据，并追溯到已确认范围或设计决定；移动操作另有目标路径。程序只用不可变调查版本的原生 Git（版本管理系统）事实核对操作动词，不读取另一个 WorkItem（建设事项）可能占用的当前工作树，也不建立第二套冲突系统。跨事项长期有效的工程文件必须显式声明稳定身份和类型，程序不按目录或后缀猜测。普通长期工程文件的后续修改、移动或删除必须引用调查提交中同一路径的可重读观察来源。若操作的是项目工程基线当前精确引用的五类项目权威，则还必须在同一评估中计划更新项目工程基线的精确引用；普通长期文件不进入项目工程基线形成通用索引。只有架构、公共接口或数据影响触发长期决定判断时才要求 ADR（架构决定记录）计划；真实长期决定使用新建或更新，不需要时明确说明理由。

若工程评估明确声明不实施，AssuranceBand（保障等级）最低可为 A0，表示本事项没有仓库交付，不是一种“调查工作模式”。Coding Agent（智能编码代理）自己的搜索、临时记录和子代理活动不进入 Strixnova。A0 仍引用已确认方向并完成紧凑 ImpactScope（影响范围），但没有真实风险、设计、操作、验证或交付计划时可以省略相应章节；不能为了填格式制造内容，也不能夹带仓库操作。程序据此不创建 Git（版本管理系统）工作区。

只要评估计划修改、创建、移动、删除或交付任何仓库文件，`formal_implementation` 就必须为 true，且 `investigation_ref` 必须是当前仓库真实可解析的不可变提交。普通工程事实的 `evidence_refs` 只能使用 `direction`、本评估已声明的 SourceReference 身份，或既有正式项目通过公开治理上下文返回的精确基线引用；方向确认记录、裸文件路径、临时调查标签都不是证据引用。`architecture`、`interface` 或 `data` 被判为受影响或未知时，必须同时提交有事实依据的方案取舍、设计决定和 ADR 候选判断。

权威变更集只处理产品定义、领域模型、目标架构和实现对齐这条四层核心目标链；工程政策继续作为独立横向约束进入评估。每条 `target_ref`（目标引用）必须属于对应权威种类的身份空间；修改、退役和更名只能指向调查提交中实际存在的身份，新增不得复用既有身份，更名后的新身份也不得已经存在。程序据此拒绝悬空引用和跨种类引用，不能只检查“填写了一个字符串”。语义复核的内容和影响程度由 Coding Agent（智能编码代理）判断，程序只检查八个视角是否齐全、引用是否真实、未解决的高影响发现是否仍被如实阻断。需要项目负责人决定的风险不能由智能编码代理自行标记为已接受，只能引用已确认方向或项目基线内指向某类精确已确认权威的引用；`baseline:project`（项目基线索引）只用于定位项目，不能冒充负责人决定。SourceReference（来源引用）、文件、测试和普通证据同样不能冒充负责人决定。

四层核心目标链使用精确修订引用，所以“正文责任不变”不能掩盖绑定变化。产品修订必须同时形成领域、目标架构和实现对齐候选；领域修订必须同时形成目标架构和实现对齐候选；目标架构修订必须同时形成实现对齐候选。程序在正式方案编译阶段确定性拒绝缺失的下游候选或错误的 `unchanged`（不变）处置。编码前的实现对齐候选绑定新上游并如实记录当前代码缺口，保持草稿；实施后可在同一事项内刷新该未确认候选，最终只随已接受实际结果机械定档。

每项正式操作和验证命令必须只归入一个 ImplementationSlice（实施切片）。完全相同的命令若位于不同切片，观察的是不同代码状态，必须保留不同命令身份并分别取得回执；只有同一切片内的完全重复命令可以归并，原始引用必须确定性映射到归并后的命令。明确无需验证命令的切片不能被程序静默当作完成：CurrentAction（当前动作）必须要求提交绑定精确操作和文件快照的显式完成记录；完成记录只说明代理已经按方案完成和复核，不证明语义正确。

长期权威候选的起草、精确正文复核和负责人确认是切片实施前的治理阶段，不是程序替智能编码代理规定的切片拆分。智能编码代理可以把产品、领域、目标架构、工程政策和编码前实现对齐安排在一个或多个有依赖的治理切片中；为了在一次确认前形成完整候选包，程序可以在任何切片产生实施证据之前允许这些候选的真实治理路径按已确认方案提前形成。该许可必须由当前候选实际声明的完整治理路径、精确修订和正文散列证明，只限长期权威、项目配置和工程基线；它不把相应切片记作完成，不允许普通业务路径提前出现，也不改变每项操作的唯一切片归属。完整候选包经八视角最终复核并由负责人逐类决定后，实施才回到普通切片依赖、路径和完成门。

已完成切片的操作结果与文件快照在后续切片、实际结果确认、结果提交和本地合入前都必须复核。工程方案只可声明一个特例：编码前已建立的同一份 ImplementationAlignment（实现对齐）草稿，可在唯一个明确的最终刷新切片中换成实施后真实散列、依赖、责任和偏离。该特例不转移原操作归属，不允许普通源码、上游权威或其他产物跨切片改写；其他需要重写前序路径的情况必须重新规划。

实现对齐的安装态应用接口固定为 `strixnova alignment prepare`、条件式 `capture-external`、只读逻辑 `inspect` 和 `write-candidate`。应用协调器必须逐次绑定当前 WorkItem 版本、已确认工程方案、首个依赖已满足的实施切片、唯一实现对齐根操作、工作树和六个计划写入路径；每个受管源码文件必须且只能匹配一个受管作用域。准备结果使用小型内容寻址清单和可分页、可去重组件保存，只承载本次机械事实和冻结语义决定合同，不成为长期权威或可变当前指针；`inspect` 必须只返回有界逻辑记录和绑定准备内容的不透明游标，不得要求 Coding Agent 理解、读取或修改清单、组件、分页和物理根目录。外部执行只能使用评估中提出并随完整方案确认的精确 provider 计划，并要求本次显式授权。provider 计划必须同时绑定 argv 以及可执行文件、入口脚本、配置和支撑文件的实际 SHA-256，程序在进程启动前重新核对材料路径、命令参数和字节并写入回执；CLI 不得接受替代命令、材料、glob、政策或资源上限。输入上限不得超过 64 MiB，输出上限不得超过 256 MiB。

Coding Agent（智能编码代理）只为 `inspect` 返回的 `semantic_decision` 逻辑记录中的精确决定引用提交源码归属、依赖分类、目标责任、偏离和未知等语义。程序机械填充路径、规范字节散列、观察节点与关系、覆盖、回执、上下游修订和代码版本，并在写入前再次比较六个目标文件的存在状态和实际字节，任何 `prepare` 后的有效编辑都必须使旧准备失效。实现对齐根、四份底账与项目工程基线必须作为一个持久日志事务替换：日志、旧文件副本和替换字节先落盘，完整候选重新读取失败或最终 WorkItem/方案/切片绑定变化时恢复所有旧文件；进程崩溃后由下一次入口恢复未提交事务，遇到第三方字节时停止而不得猜测覆盖。成功只形成 `draft` 候选，不改变 WorkItem 状态或版本，不确认、不采用，也不证明语义。覆盖不完整、provider 不可用或执行失败仍可形成结构有效但 `complete_alignment=false` 的诚实草稿，不得伪装为空依赖或完整对齐。

实现对齐缓存维护不是普通事项推进。`strixnova alignment gc --dry-run` 只能计算所有保留 preparation/capture 清单均不可达的组件集合及其内容指纹，不得写文件；`--apply` 必须提交同一指纹并在项目权威效果锁内重新计算，集合变化即拒绝。当前维护入口只能删除该精确孤立组件集合，不得删除准备、捕获、事务、长期权威或活动候选所需内容，也不得设置静默自动过期。

当非末切片的验证失败、阻断或未运行，且事后判断明确无需重测时，本轮可进入 ActualResult（实际结果），但必须标为 `completed_with_issues`（已完成但有问题），列出终止切片、全部未执行后续切片及其命令，并将这些事实写入限制；不得越级为后续切片制造回执，也不得称全部实施完成。程序可以拒绝遗漏、重复归属、依赖成环、后续路径提前出现、计划外改动、越级验证、快照失效、单向并行声明和确定性写入冲突。程序不能决定应该怎样拆分工作，也不能启动、分配或管理智能编码代理。OwnerView（负责人视图）只是同一工程方案的可读呈现，不新增第四个普通事项确认点。

评估修订时保留 `assessment_id` 并增加 `assessment_revision`。旧 EngineeringPlan 和相应方案确认随语义变化失效；程序只保留 Authority 历史，不把旧计划继续当当前事实。

## 3. SourceReference

SourceReference 只有以下事实：

- `reference_id`；
- 仓库相对 `path`；
- 可选 `line_start` 与 `line_end`；
- `observed_ref`：`working_tree` 或可解析的本地 Git ref/commit；
- `epistemic_status`：`observed`、`inferred` 或 `unknown`。

程序在声明的 working tree（工作树）或 Git commit（版本管理提交）中核验路径和行范围存在。非工作树引用会解析为实际观察时的不可变提交。程序不计算全仓快照，也不能由“文件存在”反推智能编码代理形成的语义候选正确。

既有正式项目由程序在调查提交中定位并读取实际采用的项目配置和 ProjectEngineeringBaseline（项目工程基线）；智能编码代理只有在具体语义主张使用其正文时才提交相应 SourceReference（来源引用）。新项目必须用 Git（版本管理系统）事实证明该提交尚无已采用配置。历史代码或 ADR（架构决定记录）可以引用不同提交，但这些普通来源不参与项目状态基点推断。

目标分支在实施前前进时，智能编码代理查看调查提交到目标提交之间的原生 Git（版本管理系统）差异。只有目标、范围、取舍或工程方案受到实质影响时才重新评估；无关提交不会造成全局失效。WorkflowAuthority（流程权威）只记录两个提交和智能编码代理形成的影响候选，不复制完整变化路径清单。

## 4. ImpactScope 与追溯

以下十二个维度必须各被分类一次：

1. user_behavior；
2. product_scope；
3. domain；
4. architecture；
5. interface；
6. data；
7. security_privacy；
8. quality_performance；
9. operations_deployment；
10. compatibility_migration；
11. testing；
12. documentation_support。

ImpactScope 使用三个集合：

- `affected`：每项提交 dimension、具体理由和证据引用；
- `unknown`：每项提交 dimension、未知原因和证据引用，并在 `unknowns_and_limitations` 说明影响及处理；
- `unaffected`：只列 dimension 名称，不为每项编写重复套话。

Coding Agent（智能编码代理）必须让十二个维度恰好出现一次。程序只检查总量、唯一性、枚举和引用，不把省略项猜成“不受影响”，也不根据路径、文件数、后缀或活动名称改变结论。

方向是目标、范围、约束和验收的唯一事实。操作追溯到方向范围或工程设计；验证覆盖方向验收、约束或真实风险。证据引用只保存有限锚点，不记录智能编码代理阅读了多少文件或用了什么工具。

## 5. 工程方法与 DDD 落盘合同

工程方法不是工作模式、关键词路由或额外用户流程。它使用现有三层事实：

1. 通用治理档案保存方法来源、Strixnova 自有解释、适用影响维度、技术闭集和证据要求；
2. ProjectEngineeringPolicy（项目工程政策）的 `method_adoptions`（方法采用）保存项目长期采用状态，ProjectEngineeringBaseline（项目工程基线）只定位该政策的精确修订；
3. EngineeringAssessment（工程评估）的 `method_applications`（方法应用）保存当前 WorkItem（建设事项）的智能编码代理候选，EngineeringPlan（工程方案）确定性投影该候选，ActualResult（实际结果）记录实际落实。

本期正式启用的方法只有 `ddd`。来源使用 Eric Evans 的 [DDD Reference](https://www.domainlanguage.com/ddd/reference/)；仓库只保存 Strixnova 自己的工程解释和来源元数据，不复制参考正文。来源对照不表示外部认证。

项目方法采用状态只能是 `adopted`（已采用）、`conditional`（有条件采用）、`not_adopted`（未采用）或 `not_assessed`（尚未评估）。每个正式项目始终建立并由项目工程基线精确定位 ProjectProductDefinition（项目产品定义）、ProjectDomainModel（项目领域模型）、ProjectArchitectureDescription（项目架构描述）、ProjectEngineeringPolicy（项目工程政策）和 ProjectImplementationAlignment（项目实现对齐）五类独立权威；是否采用 DDD（领域驱动设计）只改变工程政策中的方法状态，不决定这些权威是否存在。

项目全局模型先于 WorkItem（建设事项）方法应用。只有项目当前已经采用或有条件采用某方法，或同一事项明确把工程政策中的采用状态改为这两者，才能声明本事项实际应用该方法；无关领域 Fact（领域事实）变化不能冒充采用事实。程序只校验身份、闭集、引用、证据存在和结构覆盖，不把源码目录或类名机械认定为限界上下文，也不证明模型语义正确。

当项目已采用或条件采用的方法与 ImpactScope（影响范围）的受影响或未知维度相交时，Coding Agent（智能编码代理）必须明确提交 `applied`（已应用）或 `considered_not_applied`（考虑后未应用）。前者列出具体技术、使用阶段、目的、目标事实和证据；后者说明为什么本事项不应用，不生成虚假的方法使用记录。

该判断进入已有完整工程方案确认，不增加单独用户确认点，也不要求向用户朗读“采用 DDD（领域驱动设计）”。读模型保留内部确认投影，界面可以按需解释使用了什么思维。方法标签本身不提高 AssuranceBand（保障等级），不建立方法专属状态机、关键词路由、合规分数或自动重构。

项目方法采用状态变化时，EngineeringAssessment（工程评估）使用采用变化并计划修改 ProjectEngineeringPolicy（项目工程政策）与 ProjectEngineeringBaseline（项目工程基线）的精确政策引用；领域事实变化使用工程评估顶层的领域事实变化，不隶属于方法应用。领域权威维护与工程方法采用是两类独立事实：项目不采用 DDD（领域驱动设计）仍必须维护正式领域模型，应用该方法也不等于必然修改领域事实。实现对齐通过对完整 ProjectImplementationAlignment（项目实现对齐）清单及其底账产物的明确文件操作来计划，并以长期产物回执和最终完整修订闭环。新项目可以诚实选择“尚未评估”作为方法状态，但仍必须形成五类独立权威；领域或实现对齐中的未知和未实现项必须如实记录，不得伪造已完成语义。

## 6. 智能编码代理自检与专业审查边界

提交评估前，Coding Agent（智能编码代理）至少自检：

- 观察事实、推断和未知项是否分开；
- 引用是否真正支持相应判断；
- 内容是否针对当前项目，而不是模板套话；
- 是否忠实于已确认目标、范围、非目标和取舍；
- 十二维影响是否完整，受影响范围需要的操作、风险、验证、未知项和长期决定是否已经覆盖；
- 是否存在虚构事实、过度结论或为了填字段制造的工作。

这是智能编码代理完成一份高质量评估的内部工作方式，不形成任何机器复审合规状态。真实人类专业审查只有实际发生并被记录时才能称为“已经人工审查”；外部认证或合规同理。

## 7. 治理档案与标准来源

通用治理档案按需求验收、生命周期与配置、质量、测试、架构决定、安全开发、运行发布维护等主题组织。每条规则记录官方来源、准确版本、使用范围、Strixnova独立工程解释、触发维度、最低保障和所需工程信息。AssuranceBand（保障等级）不建立第二套流程：Coding Agent（智能编码代理）根据方向、影响和风险提出等级及理由，程序只应用规则中已声明的最低等级和确定性风险下限。文件数和活动名称不能提高等级，也不能据等级自动追加全量测试。

当前标准来源目录包括相关 ISO（国际标准化组织）、IEC（国际电工委员会）、IEEE（电气与电子工程师协会）标准和 NIST（美国国家标准与技术研究院）安全开发框架。每项同时记录官方版本核实依据、版权或使用状态、允许使用边界和内容边界。受版权保护的标准只保留书目信息、官方链接与 Strixnova独立工程解释，不复制或向智能编码代理提供标准正文；允许公开使用的来源按其许可边界引用。来源状态变化时必须重新核实，不能依赖模型记忆。

项目可以在 ProjectEngineeringPolicy（项目工程政策）中增加项目规则、提高最低保障，或以项目负责人确认的理由声明某条通用规则对项目不适用。ProjectEngineeringBaseline（项目工程基线）只定位该政策的精确修订；程序只执行已记录裁剪，不能临时替用户降低底线。

ProjectEngineeringAssurance（项目工程保障评估）是绑定精确五权威链、治理档案版本和证据基线的下游内部评估产物，不是第六项长期权威。它必须逐条覆盖治理档案中的规则，分别记录适用性、内部状态、证据、缺口、纠偏和限制；不计算会掩盖单项缺口的总分。程序只校验身份、来源覆盖、证据路径与内容摘要、逐项状态约束和外部回执边界；规则是否真正满足仍由智能编码代理形成候选，并向使用者如实展示证明限制。

标准来源绑定只说明采用依据可定位，不能推出项目语义正确。没有独立外部回执时，外部保障状态必须保持“未声明”；即使存在回执，程序也只证明回执文件和引用存在，不能代替签发方解释其适用范围。

## 8. VerificationCommand

Coding Agent（智能编码代理）明确提交：

- `argv`：不经过 shell 的精确参数数组；
- `cwd`：实施工作树内相对目录；
- `run_kind`；
- `covers`：已确认方向中的验收/约束或风险字段路径；
- `reason`；
- 可选 `optional_timeout`。

程序只按规范化的参数数组、工作目录和运行种类去重，并合并覆盖目标与理由。它不猜测测试框架或构建工具，不按 AssuranceBand（保障等级）自动追加全量套件。全量回归只在智能编码代理评估或已确认项目工程政策明确要求时出现。

`not_run`（未运行）只表示命令没有执行，必须给出原因和限制，不能算通过。实际执行先生成不带变化结论的回执；命令结束后智能编码代理再查看普通 Git（版本管理系统）差异，提交执行后变化、是否需要重测及理由。尚未事后判断或明确需要重测的旧回执不能支撑 ActualResult（实际结果）。

没有适用测试规则或项目政策时，评估可以选择零条验证命令，但必须提交具体的不需要验证理由。此时聚合状态为“无需验证”，ActualResult（实际结果）不引用回执；这与漏掉计划命令或伪装成通过不同。纯说明性文档若不改变机器读取的配置、Schema（结构合同）、可执行示例、生成产物或路径行为，且项目没有适用的真实文档构建、链接检查或示例执行工具，应诚实选择零条命令；不得临时拼接关键词、正则或路径存在性检查来制造测试回执。文档语义准确性由智能编码代理审查并交由用户确认，不得宣称已被程序证明。机器读取的文档或已有真实工具覆盖的行为仍在最低有效层验证。

验证聚合只公开一个 `verification_status`：`not_required`、`pending`、`passed` 或 `completed_with_issues`。失败、阻塞和 not_run 在完成事后判断后属于 `completed_with_issues`，必须进入实际结果限制，不能称为通过。能否进入下一步只由 CurrentAction 表达，不再并列输出 `all_passed` 与 `ready_for_actual_result`。

## 9. EngineeringPlan 与诚实结论

EngineeringPlan（工程方案）同时引用当前方向版本以及 `assessment_id`（评估标识）和 `assessment_revision`（评估修订），列出 ChangeContext（变更上下文）、ImpactScope（影响范围）、权威变更集、语义复核、实施切片、负责人视图、适用规则、追溯引用、经规范化去重的完整验证命令及其确定性 ID（标识），以及最终 AssuranceBand（保障等级）。方向事实和评估正文都只有一份，方案不复制同一语义。第三版方案删除笼统的符合性布尔组，只保留逐项适用规则和“机器未证明语义”边界。

ActualResult（实际结果）必须为方案中的每条适用规则提交一个 GovernanceRuleAssessment（治理规则评估结果）。状态为满足时必须引用真实结果证据且不能同时保留缺口；部分满足、不满足或未知时必须同时记录缺口与明确纠偏行动，并把限制呈现给用户。程序验证逐条闭合和证据引用，不生成状态、不计算总分。

程序能证明的是结构、引用、关系、逐项覆盖和已声明规则已通过确定性校验。它不能证明全部软件语义正确，也不能把智能编码代理自检等同于真人专家审查或外部认证或合规。

新项目在评估时可以尚无 ProjectEngineeringBaseline（项目工程基线），先使用通用治理档案；评估必须一次声明 `project_engineering_baseline_path`（项目工程基线位置）、`project_product_definition_path`（项目产品定义位置）、`project_domain_model_path`（项目领域模型位置）、`project_architecture_description_path`（项目架构描述位置）、`project_engineering_policy_path`（项目工程政策位置）和 `project_implementation_alignment_path`（项目实现对齐位置）六个仓库位置，并明确计划创建项目配置、项目工程基线以及五类独立权威。是否采用 DDD（领域驱动设计）只改变工程政策中的方法采用状态，不决定是否建立领域模型或实现对齐。ActualResult（实际结果）展示前，程序从实施工作树重新读取完整权威链，验证结构、精确引用、版本和覆盖；程序不替 Coding Agent（智能编码代理）编写项目目的、领域、架构、政策或实现判断。

ProductDefinition（产品定义）、DomainModel（领域模型）、TargetArchitecture（目标架构）和 EngineeringPolicy（工程政策）的首次定档或实质修订，必须在正式实施前通过独立长期权威决定完成确认并由项目工程基线采用。ActualResult（实际结果）接受只能授权 ApplicationCoordinator（应用协调器）通过公开交付入口机械确认与本轮代码和证据精确绑定的 ImplementationAlignment（实现对齐）候选；确认日期取自该实际结果确认事件。程序和智能编码代理都不得用普通结果确认补写上游权威的确认状态或基线采用引用。

每类变化的上游长期权威必须先通过公开 `strixnova authority`（Strixnova长期权威决定命令）按产品、领域、目标架构、工程政策的依赖顺序读取精确候选并记录展示；全部待决候选都已展示后，CurrentAction（当前动作）必须先要求智能编码代理提交一份八视角最终候选复核。该复核逐类绑定候选身份、精确修订、全部治理路径的规范正文散列和同一工程方案；正文变化立即使复核失效。程序只校验结构、引用、散列和阻断状态，不判断复核语义，也不新增负责人确认点。复核闭合后，CurrentAction 一次返回包含多项有意义决定文本和内部候选绑定的确认包。负责人只阅读候选语义以及逐类接受或退回句，可在一条后续消息中逐类决定；智能编码代理不得展示或要求负责人复制内部指纹，而应从 CurrentAction 机械取得各项指纹，并用一次 `strixnova authority --input`（Strixnova长期权威决定命令输入）连同负责人原文提交完整决定数组。程序内部仍按依赖顺序原子处理，每类决定保留独立身份；政策只依赖已接受产品，不因领域或架构被退回而无关失效。程序只在内部候选绑定、负责人语义决定原文、候选正文、精确上游正文、已确认工程方案、最终候选复核和负责人身份完全一致时，原子写入确认元数据并保存决定与确认后正文散列；智能编码代理不得手工写入 `confirmed`（已确认）、负责人或日期。ActualResult（实际结果）提交时必须反查每类变化的上游权威决定及当前正文，缺失、代签、状态先改、候选替换或接受后改写都必须拒绝。

新项目或权威修订在项目负责人接受完整精确候选后、写业务代码前，可以显式运行 `strixnova status --working-tree`（Strixnova工作树候选检查命令）。该入口只读取当前未提交工作树，校验项目配置、第三版项目工程基线、五类权威的结构、身份、精确引用、状态和覆盖，并把输出标记为 `working_tree_candidate`（工作树候选）与 `candidate_only: true`（仅为候选：是）。它不取得写权、不改变采用状态、不证明语义正确，也不改变默认 `strixnova status`（Strixnova项目状态命令）仍只读取不可变本地集成版本的规则。`--working-tree`（工作树候选）与 `--at-commit`（指定不可变提交）不得同时使用。

实际结果展示时要同时形成 AuthorityCandidateSnapshot（权威候选快照）和 ImplementationCandidateSnapshot（实施结果候选快照）。前者保护五类长期权威与项目基线，后者保护已完成或终止切片的普通交付文件，并明确排除未执行后续切片。两份快照都要在实际结果确认、结果提交和真正本地集成提交形成后复核；只有实际结果明确授权的实现对齐确认元数据和项目基线引用可由程序机械变化，普通交付文件不在豁免范围。若原生 Git（版本管理系统）合入发生内容冲突，智能编码代理必须先明确报告是否改变已确认方向、方案或用户可见结果：任一改变都必须重新规划或重新展示实际结果；三者均未改变时，全部受影响验证通过并完成事后判断后，程序可以形成 ConflictResolutionCandidateSnapshot（冲突解决候选快照），只替代冲突影响的普通交付文件证据，并要求真正合入提交与该快照完全一致。它不得替代或放宽长期权威候选快照。集成后复核必须从不可变 Git（版本管理系统）提交读取规范字节；快照不一致时不得记录本地合入完成。工作树规范字节计算不得执行仓库声明的外部 `clean filter`（提交前转换器）、`ident`（对象身份展开）或 `working-tree-encoding`（工作树编码转换）；发现这些显式属性时必须稳定阻断，而不是把属性值为 `unset`（取消设置）或 `unspecified`（未指定）的文本误当成安全状态。
