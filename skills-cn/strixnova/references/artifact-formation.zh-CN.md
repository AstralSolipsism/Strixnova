# 为当前决定形成工程产物

只有请求仍有实质模糊、交付跨度不确定、用户要求熟悉的规划产物、正在出现跨单元架构选择，或发现的上游错误可能使下游失效时，才读取本资料。对于边界清楚的单 WorkItem（建设事项），直接使用普通方向和工程评估资料，不加载本文件。

产品或功能想法本身还不足以命名具体事项时，先读 `product-discovery.md`；只有交付跨度、熟悉投影或长期跨单元选择仍需处理时，才返回本资料。

载荷结构使用当前 `CurrentAction.input_contract_ref`；本资料帮助选择形成深度、交付跨度和可读产物。

## 先从证据出发，再找真正缺少的决定

用户原话是意图证据，不是天然完整的规格，也不能被机械扩写。提问以前：

1. 只调查当前决定真正需要的已采用产品、领域、架构、工程政策、实现对齐、相关项目资料和代码；
2. 分开项目可以回答的事实和只有项目负责人才能作出的选择；
3. 找到最上游、且会实质改变目标、边界、取舍、成功条件或下游权威的未决选择；
4. 直接形成现有候选，或者只问一个决定问题，同时说明推荐、用户可见影响和不处理后果。

不要让负责人提供 Agent 可以调查的文件位置、框架细节、领域术语、测试命令或当前行为。下游已经不需要发明关键决定时，停止继续探索。

## 分别判断三个独立裁剪轴

规划不能压成一个由小到大的等级。每个适用轴都要用当前项目事实解释。

| 裁剪轴 | 要回答的问题 | 依据 | 现有落点 |
|---|---|---|---|
| 需求形成深度 | 下游是否还要猜客户、问题、边界、重大取舍或成功条件？ | 用户意图、已采用权威、项目证据和未决决定 | 对话、长期权威候选或 DirectionDecision（方向决定）候选 |
| DeliverySpan（交付跨度） | 最少需要几个能分别提供价值并独立接受的结果？ | 独立价值、共享决定、先后依赖和跨单元协调 | 一个 WorkItem、有关联的多个 WorkItem 或项目级权威形成 |
| 保障深度 | 每个结果需要多深的调查、审查和验证？ | 影响、风险、可逆性、不确定性和项目政策 | EngineeringAssessment（工程评估）与 AssuranceBand（保障等级） |

文件数、代码行数、预计会话数、产物名称和活动名称只能帮助调查，不能决定任何一个轴。单文件的不可逆数据变化可以保持一个 WorkItem 并采用较深保障；涉及很多文件但机械、可恢复的改动也不必采用最高保障。

## 在同一种合同内选择交互节奏

目标、边界、适用产品护栏和验收已经明确时，使用快速起草。调查事实，写清重要假设，直接形成现有候选，只展示真实存在的剩余决定，不制造问题。已采用项目复用有效权威，只更新受影响内容；PRD、SPEC 等阅读产物按需形成。

项目首次接入的正式仓库交付仍需完整建立基础权威，遵循
[engineering-assessment.md](engineering-assessment.zh-CN.md) 的首次接入边界。
Agent 调查并复用已有资料，内容深度与项目规模相称；负责人处理实质决定，不填写模板。

客户、问题、预期结果、边界、重大取舍或成功条件仍有关键不确定时，使用逐项辅导。从上游选择到下游选择，一次只解决一个决定；一轮形成过程最多保留五个真正高影响的问题。负责人每次纠正后重新判断，能够安全形成同一种现有候选时就停止。

这两种做法只是交互节奏，不是模式。它们都进入相同的长期权威、DirectionDecision、EngineeringAssessment 和确认合同，不要求用户先选择 Strixnova 规划模式。

## 按可独立接受的结果判断交付跨度

- 请求可以作为一个完整结果接受时，使用一个 WorkItem；它可以包含多个有依赖步骤，也可以具有高风险。
- 每个结果都有独立用户价值和验收、可以分别交付，且不需要其他结果完成才能声称自己完成时，建议多个 WorkItem。只有目标和项目特定关系已经真实存在时才声明现有 WorkItemRelation（建设事项关系）。
- 多个结果共同依赖一个尚未决定的产品选择或跨单元架构选择时，先形成或修订项目级权威，再进入各 WorkItem 实施。

Story（故事）对应一个可独立接受的 WorkItem 候选。ImplementationSlice（实施切片）是一个已确认 WorkItem 方案里的内部步骤，不要把内部步骤当成额外 Story。现有 WorkItem 关系只提供追溯，不提供 Epic（史诗）聚合接受、组合进度、排期或 Agent 编排。

## 把熟悉产物映射回现有权威

熟悉名称只帮助思考或阅读，不能建立另一份可编辑真相。

| 熟悉表达 | 正式含义进入 | 边界 |
|---|---|---|
| Product Brief（产品简述）或 PRFAQ（新闻稿与常见问题） | ProjectProductDefinition（项目产品定义）和 ProjectDomainModel（项目领域模型）候选 | 只是可选的探索视角；长期事实进入真正拥有它的权威 |
| PRD（产品需求文档） | 精确产品、领域和必要架构修订的只读组合 | 标明来源修订；先修订来源权威才能改变含义 |
| SPEC（规格） | DirectionDecision 与相关 EngineeringPlan（工程方案）的只读组合 | 没有独立状态、确认或写权 |
| Architecture Spine（架构骨架） | ProjectArchitectureDescription（项目目标架构描述）或 ADR（架构决策记录）候选 | 只保留有真实长期取舍的跨单元选择；局部可逆选择留在方案中 |
| Story（故事） | 一个可独立接受的 WorkItem 候选 | 不是 ImplementationSlice |
| Epic（史诗）或 Initiative（项目倡议） | 当前没有一等 Strixnova 对象 | 已知关系只用于 WorkItem 追溯，不声称具备聚合接受或调度 |

内置产物形成指引可以使用部分 SDD（规格驱动开发）写作技术。这不证明受管项目采用了 SDD 或其他 EngineeringMethod（工程方法）。只有项目自身确实需要形成长期方法决定时，才在 ProjectEngineeringPolicy 中记录采用状态。

PRD 的实质形成、整理、审阅和更新读取 [prd-authoring.md](prd-authoring.zh-CN.md)；对应的变化
规格工作读取 [spec-authoring.md](spec-authoring.zh-CN.md)。两者共用
[artifact-documentation.md](artifact-documentation.zh-CN.md) 的来源与更新规则，只加载当前请求
需要的专门资料。请求写阅读产物且已获授权、来源足够时必须实际写出，映射表不算交付。
候选阅读表达在现有负责人决定之前就必须说明真实来源和状态。

## 处理常见的困难情形

| 情形 | 推荐形成方式 | 必须避免 |
|---|---|---|
| 清楚、边界明确的改动 | 调查后直接形成单 WorkItem 方向；首次接入时遵循基础权威要求 | 无必要的 PRD、重建有效权威或仪式性问题 |
| 无法识别具体变化的模糊愿望 | 先建立用户、问题、预期结果和关键边界；能够命名具体事项后再创建 WorkItem | 把 Agent 猜测写成需求 |
| 具体但不完整的请求 | 按用户要求创建 WorkItem，再在方向阶段只关闭实质缺口 | 在 `intake` 前做一轮影子访谈 |
| 一个高风险结果 | 验收是一个整体时保持单 WorkItem，在 EngineeringAssessment 中加深保障 | 只因风险高就拆分，或只因差异小就降低保障 |
| 多个有独立价值的结果 | 说明共享目标，提出具有独立验收的相关 WorkItem | 把 ImplementationSlice 称作用户价值 Story |
| 跨单元架构冲突 | 在依赖它的实施前形成目标架构或 ADR 候选 | 让每个 WorkItem 各自发明不同长期决定 |
| 上游含义被证明错误 | 修订拥有该含义的产品、领域或架构权威，用 AuthorityChangeSet（权威变更集）处置每项下游影响 | 只修补 PRD、SPEC、Story、OwnerView（负责人视图）或实施计划 |

## 复核形成结果

展示候选以前检查：

- 每条长期有效的陈述都有且只有一个现有权威负责；
- 只读投影标明精确来源修订，不能作为竞争真相单独编辑；
- 推荐交付跨度来自可独立接受的结果，而不是文件数、工作量、风险或内部步骤；
- 每个 WorkItem 的保障深度根据影响和政策单独选择；
- 需求、场景、验收、架构决定、WorkItem 和 ImplementationSlice 没有遗漏或矛盾；
- 负责人纠正后，所有受影响下游候选都已失效并重新形成；
- 面向用户的说明讲清已知事实、真实缺口、推荐及理由、影响、不处理后果和下一个现有 Strixnova 动作，不把内部标识当成含义。

这项复核仍是 Agent 判断。Strixnova 可以校验现有结构、引用、版本、状态和已声明证据边界，但不能证明自然语言语义正确。
