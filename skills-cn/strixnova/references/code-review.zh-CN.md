# 对照工程规范与预期行为审查代码

用户请求代码审查、规格与实现比较，或当前方案、工程政策要求代码复核时读取。正式权威或
方案复核同时使用[跨产物审查](cross-artifact-review.zh-CN.md)中适用的程序；非正式只读代码
审查可以不创建 WorkItem，也不额外进入该程序。

## 明确实际比较范围与来源

用户已授权使用 Strixnova 上下文且项目已有登记权威时，先读 `strixnova context contract review`，
再用 `strixnova context review --project-dir <project> --input @<request.json>` 取得资料。
`mode: changes` 用于明确的变更比较，`mode: modules` 配合已取得的模块身份用于无 diff 的定向审阅。
每个仓库分别指定 `ref`（`null` 表示工作树），改动查询还需 `base_ref`。`basis_ref` 选择权威依据，
省略则使用项目配置的集成引用；本机绑定沿用已有明确声明。

查询不创建 WorkItem 或执行审阅者，只沿登记归属和显式关系提供资料；语义相关性和缺失依赖仍由
Agent 调查。必须同时看 `sources`、`gaps`、`omitted_files`、内容窗口及
`recorded_observation_current`，区分已采用规则、候选、历史观察和当前代码。
`status: available` 不代表审阅通过。资料缺失允许有限审阅；身份或版本冲突需要纠正输入。
不得为获取背景自动初始化治理、刷新对齐或安装另一审阅工具。审阅者需要背景文档时，
`--format markdown` 只渲染同一份事实，不产生新权威。

根据请求和现有事实定位比较基点，再确定目标是提交、分支结果还是当前工作树。审查工作树
时纳入相关已暂存、未暂存变化和新文件，只比较已提交 HEAD 会漏掉请求范围。尊重无关变化
的归属，读取足以判断影响的周边代码和调用方。区分新引入问题与既有问题，但也检查本次变更
是否让旧问题变得可触达。

读取真实需求及适用工程规范。优先使用所属的已确认方向、方案和长期权威，SPEC 阅读版须
与这些来源一致。非正式审查可以按原身份使用用户提供的需求，不伪造权威身份或确认状态。
来源缺失或矛盾时说明限制，只评估已知部分；只有比较范围或产品决定会改变结论时才询问。

审查授权不等于修复、格式化、安装依赖、采用来源或 Git 交付授权。尊重不运行测试的要求。
允许命令时使用适用的现有工具并限制副作用，区分工具结果与未运行检查。仅在用户请求或当前
项目工作流要求时写报告文件。

## 检查规范与设计

以项目真实规则作为违反规范的依据。格式和类型等工具规则可以引用实际工具结果。模块责任、
依赖方向、错误处理或可维护性需要 Agent 阅读代码并解释后果；风格偏好或代码气味属于设计
判断，不是已采用规则，也不自动构成缺陷。

检查变更是否把协调工作散布给调用方、绕过所属接口、增加无用泛化、重复策略，或者使测试
依赖私有结构。沿线索查到足以说明真实问题，不为套用外部方法要求抽象、改名或重写。
模块或测试边界判断需要更多方法时，才读[实施与测试方法](implementation-practices.zh-CN.md)。

## 检查规定行为与相应证据

发现的范围不能超过实际检查的路径和条件。入口绕过规定服务，可以证明这处调用路径违规；
但不能单凭这一点证明未展示的数据仓库接受写入，或每个调用者都能利用它。完整代码路径
可以在没有运行测试时证明静态后果；执行记录则证明其实际身份、输入和环境下发生了什么。
说明发现由哪种证据支持。模块归属缺失或依赖观察过时属于具体缺口，不是已证实的禁用依赖；
判定违规前须确认依赖两端及适用规则。下游影响未验证，不应删除已有依据的局部发现；
已有执行事实也应保留其确切范围。

把每项重要变更需求的条件和结果追溯到实现、相应断言或实际运行。检查适用的边界、拒绝、
重复、失败和恢复路径，以具体例子指出缺失、部分、矛盾或未请求行为。函数名、关键词、合法
引用或命令成功退出，都不足以认定需求得到满足。

判断测试能否区分承诺行为和疑似错误行为。命令的 covers 字段列出多项要求，不证明断言真的
测试了全部要求。缺少测试与已经展示的实现错误分开报告，解释重要的未测风险，不要求每行
代码都配一个测试。区分可观察验收与仍需后续使用或测量的业务结果。

纠正后使用新代码及仍适用来源，重验受影响发现与关联行为；修复后不沿用旧指责，也不能只因
文件发生变化就标记问题解决。

## 报告发现并沿用既有纠偏路径

即使由同一 Agent 完成，也分别呈现规范与设计发现、规格符合性发现。正确实现可能违反项目
规则，规整代码也可能实现了错误需求。说明精确范围，每项重要发现给出位置、规则或需求、
可观察后果、证据和有效修正。继续正式复核时沿用既有发现身份。不强凑问题数量，不把未知
伪装成违规；审查可以没有可行动问题。

独立复核确有必要且宿主允许时，Agent 可以按宿主规则委派。这仍是 Agent 证据，不是真人专家
审查或 Strixnova 编排。不建立审阅者注册表、平行清单权威、质量评分或额外用户确认。

按真实输入合同把适用发现和限制写回现有语义审查、方案或实际结果。实现缺陷在实现中修复，
产品或架构决定回到其所属主体，不降低规格迁就代码。Strixnova 校验已声明引用、当前版本及
未解决阻断状态，不判断 Agent 结论是否正确，也不宣称找出了全部可能缺陷。
