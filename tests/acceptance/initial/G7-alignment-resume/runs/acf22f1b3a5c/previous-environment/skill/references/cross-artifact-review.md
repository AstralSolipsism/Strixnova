# 跨产物审查与负责人展示

本规程用于长期权威候选、工程方案候选和实际结果的只读语义复核。审查结论由智能编码
代理形成，不是程序证明，也不是新的长期权威。

## 什么时候必须审查

- 新项目首次形成产品、领域或目标架构候选；
- 现行产品、领域、目标架构或实现对齐发生修订；
- 工程评估把产品范围、领域或架构列为受影响或未知；
- 实施中新事实可能使已确认方向、长期权威或工程方案失效；
- 用户明确要求检查领域完整性、架构漂移、权威污染或实施就绪程度。

只读审查可以在没有文件变更时进行；若要进入正式实施确认，阻断性发现必须先关闭。

用户请求代码差异审查、规格与代码对照，或当前方案要求代码复核时，再读
[code-review.md](code-review.md)。该规程指导 Agent 分别检查工程规范和需求符合性；
不把八视角记录变成程序代码审查，也不要求每次文档审阅都加载代码复核资料。

审阅交互说明、原型或影响用户体验的关键流程时，按需读 [ux-design.md](ux-design.md)。
遇到接口、权限、并发、兼容或恢复的实质风险，再读
[behavior-contracts.md](behavior-contracts.md)；不要求普通文档审阅遍历所有技术专题。

方案含行为例子时，按[行为例子与核验](behavior-examples.md)核对上游依据、原生用例绑定、
断言充分性和实际执行。测试已存在、某次命令通过和断言覆盖了承诺是不同结论，不能互相代替。

## 固定八个审查视角

1. **产品到领域覆盖**：每项本轮产品能力和范围变化，是否都有完整领域解释？
2. **术语、决定权、规则和不变量**：是否一词多义、职责冲突、规则遗漏或不变量互斥？
3. **领域到架构处置**：每项受影响领域事实是否有唯一架构处置，是否出现共同负责或悬空？
4. **方案与实施切片覆盖**：每个目标是否有文件操作、建设切片、完成条件和适用验证？
5. **孤儿内容与权威倒置**：是否存在无上游依据的模块、任务、文件操作，或用代码、测试、
   外部模板、智能编码代理建议反向改写权威？
6. **场景覆盖**：正常、阻断、纠正、取消、恢复和失败是否充分，确实不适用时是否说明？
7. **非功能与风险覆盖**：性能、安全、兼容、发布、部署、运行和维护是否按真实影响进入方案？
8. **证据与结论边界**：哪些是观察事实、智能编码代理判断、负责人确认、实际效果或外部结论，
   是否被错误混为一谈？

不得因为八项都填了就声称语义正确。每项的严重程度、说明、影响和建议仍是智能编码代理
判断；程序只检查八项是否齐全、发现是否被引用、状态是否闭合。

## 从内容中诊断具体问题

判断两份材料矛盾前，先核对它们是否约束同一个对象、同一身份或范围、同一时间条件，
以及各自是草稿还是已经采用的规则。对象尚不明确时，报告潜在冲突和需要核实的区别，
不能直接断言运行必然失败；已经明确同一对象且条件互斥时，应指出冲突，不用臆造备份、
替代路径或例外来回避。草稿之间的差异不是已违反客户承诺的证据。
例如“删除输入数据”和“保留生成结果”只有在对象与来源关系明确后才能判断是否互斥。
已采用的规则已经清楚时，下游草稿或实现应在现有授权范围内按该规则修正，不能把
“遵守现行规则还是另换规则”重新交给负责人选择。当前只获准审阅时，只报告修正建议，
不自行实施。只有确有理由改变上游含义或取舍时，才向拥有该决定的权威提出修订候选，
沿既有确认流程处理；不能用审查建议直接覆盖已采用约束。

按下游影响判断发现，不按栏目数量或文档篇幅判质量。以下是需要依据的诊断线索：

| 线索 | 要核对什么 | 不应直接下的结论 |
| --- | --- | --- |
| 功能很多，却无法作取舍 | 当前主张、优先级和边界是否能支持这一次实施决定 | 功能多必然过度设计 |
| 正文流畅，却丢掉用户输入 | 对照实际来源，指出哪项承诺、限制或否定条件在整理时丢失 | 文字简短必然不完整 |
| 阈值看似精确，却无依据 | 该值来自现行合同、观测、负责人选择还是未经说明的假设 | 没有数字就不能实施 |
| 指标可能鼓励错误行为 | 按指标优化会不会违反目标，例如只压低工单数量却漏掉待处理请求 | 商业结果指标可以代替本次可验证验收 |
| 覆盖声明齐全，行为却没被验证 | 追踪具体条件、实现和断言，检查未覆盖异常及反例 | 引用或检查项勾选即代表实现充分 |

对有依据的发现给出位置、后果和可执行纠正；区分阻断当前实施的未决与可按责任、条件和
复查时机延期的未决。合格内容允许没有发现，修订后重新判断，不沿用已经失效的指责。

## 怎样形成审查报告

使用 `strixnova.semantic-review.v1`（Strixnova语义审查第一版）结构：

- `reviewed_refs`（已审查引用）只写当前确实读取的精确候选与证据；
- `checks`（审查项）恰好覆盖上述八个视角；
- `findings`（发现）记录稳定身份、视角、严重程度、状态、位置、说明、影响、建议、是否需要
  负责人决定和处置结果；
- `question_budget`（问题预算）固定最多五个问题；
- `resolved_decision_refs`（已解决决定引用）只能引用已确认方向或项目基线中指向某类精确
  已确认长期权威的引用；`baseline:project`（项目基线索引）只定位项目，不是负责人决定。
  `source_references`（来源引用）、文件、测试、审查发现和代理建议只能作为证据，不能冒充
  负责人决定；
- `semantic_content_machine_proven`（语义内容由机器证明）必须为 `false`（否）。

低或中等影响、无需负责人决定的发现可以保持开放并进入实施，但必须在限制中可见。高或
严重影响发现、任何需要负责人决定的开放发现，以及仍未解决的高影响决定，都会阻止正式
方案进入确认。

## 最终长期权威候选怎样复核

工程评估中的 `semantic_review`（语义复核）审查的是方向、变化范围和计划，不能冒充对
后来才写成的长期权威正文做过复核。全部计划候选已经逐类记录展示后，CurrentAction
（当前动作）会进入 `review_project_authority_candidates`（复核长期权威候选）阶段：

1. 运行一次不带 `--authority-kind`（权威种类）和 `--input`（输入）的
   `strixnova authority`（Strixnova长期权威命令），只读取当前完整候选包；
2. 逐一读取它列出的产品、领域、目标架构、工程政策和实现对齐治理路径，按同样八个视角
   形成新的 `semantic_review`（语义复核）；
3. `reviewed_refs`（已审查引用）必须原样覆盖候选包给出的每个精确引用。每个引用已经绑定
   权威种类、稳定身份、修订和全部治理文件的规范正文散列，不能用根路径、计划引用或旧审查
   代替；
4. 用一份 `strixnova.project-authority-review-submission.v1`（Strixnova项目长期权威复核提交
   第一版）输入提交复核。这个动作记录代理审查，不请求项目负责人决定；
5. 任一候选正文、治理路径或上游绑定变化后，旧复核自动失效，必须重新读取并复核完整包。

程序只证明“复核记录绑定了当前完整候选”，不证明审查文字或候选语义正确。复核闭合后才
进入负责人完整确认包；这不增加第四个普通事项确认点。

## 怎样避免几十次零散确认

1. 先自行调查项目和环境中能确定的事实，不问用户文件路径、工具名称或当前实现情况。
2. 内部汇总全部未知，按“影响大小乘以不确定程度”排序。
3. 合并本质相同的问题；能由已确认上游事实推导的，不再询问。
4. 每次只问一个会实质改变产品、领域或重大架构方向的问题，并同时说明推荐答案、影响和
   不处理后果。
5. 一次集中讨论最多五个问题。达到预算仍有高影响未知时，明确剩余问题并保持候选未定档，
   不继续追问，也不假装已经完整。

用户对单个问题的回答只解决该决定，不等于确认随后形成的完整方向、长期权威、工程方案
或实际结果。

## 实施切片怎样通过就绪审查

每个 `implementation_slice`（实施切片）必须：

- 有唯一身份和一个可理解的目的；
- 追溯已确认范围、约束、验收、设计决定、长期权威变化或已处置审查发现；
- 精确拥有一组文件操作，且所有操作只归属一个切片；
- 声明前置切片；并行安全必须双向声明，且不能存在依赖或写入路径冲突；
- 有可观察完成条件和失败后的恢复办法；
- 归属适用验证命令。前置治理切片可以没有命令，并以显式完成记录闭合；只有整个正式变更
  都没有可运行命令时，工程评估才填写顶层不适用原因，不能伪造验证。

智能编码代理决定怎样拆分和怎样实施。Strixnova程序只检查身份、覆盖、依赖、
循环、并行声明和确定性写入冲突；它不会启动、调度或管理智能编码代理。

如果方案需要建立或修订长期权威，候选起草、上述最终正文复核和负责人确认先作为切片实施前
的治理阶段闭合。候选可以按 Agent（智能编码代理）设计分散在多个有依赖的治理切片，但为了
一次复核和确认，全部计划候选治理路径可以在任何切片产生实施证据前先写齐；这只形成候选，
不完成切片，也不允许普通源码、测试或其他业务路径提前出现。候选确认后仍按原切片依赖、
完成条件和文件快照推进。

## 给项目负责人怎样讲

先用自然中文说明推荐或实际变化，不先倾倒字段表、文件清单或百分比。工程方案和实际
结果的说明覆盖以下内容；按本次决定组织，不要求把每个字段变成独立标题：

1. **决策支持**：当前问题、为什么重要、影响、推荐、替代选择、不处理后果、下一步，以及
   最多五个当前确有必要的问题；没有必要问题时使用空数组，不制造追问；
2. **工程上下文**：产品与领域改变、架构责任、实施顺序、最高影响风险、验证和可观察效果、
   仍未知或不能证明的内容；
3. **当前唯一决定**：只提出当前关口真正需要的决定，不追加新的仪式性确认。

工程评估中的 `owner_view`（负责人视图）固定承载上述决策支持和工程上下文。它是智能编码代理形成的自然语言
说明，程序只检查栏目齐全、字符串非空、必要问题不超过五个和“语义未由机器证明”的边界。实际结果展示要用真实回执和现状
更新验证、可观察效果和未知，不能照抄方案中的未来时表述。面向负责人的简洁说明不减少
完整记录的字段、审查发现和证据；每组约五项的阅读建议不能截断重要内容或独立决定。

结果说明先对照预期说明实际变化，再把会影响接受的未完成项和限制放在相应结果旁边。
例如，题面事实确实如此时：“筛选导出已完成，字段与当前列表一致；本地回归通过，生产
数据规模下的耗时尚未验证。”随后说明该限制对本次验收的影响、依据与当前决定，不能只
保留前半句宣称全部完成。不要为突出进展编造耗时、失败原因或额外的后续承诺。

## 发现需要纠偏时退回哪里

| 发现 | 退回位置 | 不应做的事 |
|---|---|---|
| 产品目的、范围或成功判断错误 | 产品定义或事项方向 | 不用领域或代码补写产品决定 |
| 术语、规则、决定权、场景或不变量缺失 | 领域模型 | 不让架构猜业务含义 |
| 责任归属、依赖方向或领域处置错误 | 目标架构 | 不用当前文件布局定档未来责任 |
| 上游正确但文件操作、切片、验证或风险遗漏 | 工程评估新修订 | 不修改已确认方向制造假变化 |
| 实施与已确认方案不一致 | 停止当前切片并重规划 | 不继续执行后续切片掩盖偏差 |
| 只有当前实现偏离目标 | 实现或实现对齐 | 不反向降低上游目标迁就代码 |

纠偏后重新审查受影响分支和所有下游，不机械重问已经回答且没有失效的决定。
