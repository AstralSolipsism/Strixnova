# 长期权威建模与对齐

只在形成或审查产品、领域、目标架构或实现对齐的含义时读取本文件。正式结构与操作顺序由对应合同和起草资料说明。

先读取 [authority-authoring.md](authority-authoring.md)（长期权威起草资料包）判断本次是首次建立、修订现行权威还是只读审查，并取得五类正式结构的公开写作检查表。需要跨产物审查、问题预算、实施切片或负责人展示时，再读取 [cross-artifact-review.md](cross-artifact-review.md)（跨产物审查与负责人展示）。

## 先确定载体与当前状态

- 长期权威必须保存在项目自己的版本化正式文件中，并由项目采用记录引用；不保存在本技能、说明文档、对话、建设事项数据库或当前代码里。
- 先运行 `strixnova status`（Strixnova项目状态命令），判断项目是否已经采用长期权威。已有项目只使用状态结果和正式采用记录给出的精确路径、修订与状态，不能凭文件名猜测。
- 状态中的 `confirmed`（已确认）表示项目负责人确认过该精确修订；`draft`（草稿）或 `ready_for_confirmation`（待确认）都不能作为下游定档依据。
- 受管新项目先在普通建设事项的工程评估中使用 `create_project`（创建项目）变更类型，并按当前 `input_contract_ref`（输入合同引用）规划项目采用文件、工程基线、产品定义、领域模型、目标架构、工程政策和实现对齐的精确路径；工程方案确认前不得抢先创建或猜写这些文件。
- 工程方案确认并建立实施空间后，智能编码代理按本文件顺序用正常工程工具形成正式候选。`strixnova authority`（Strixnova长期权威命令）负责记录候选展示、绑定精确正文的复核和完整决定包；负责人接受后，程序只机械写入确认元数据。实际结果提交前，由 Strixnova检查项目采用记录、引用链和结构。
- 如果用户只授权分析或候选设计而没有启动受管建设事项，可以交付可审查文档，但必须明确“尚未写入项目正式载体、尚未定档”，不得声称 Strixnova已经采用。

## 守住单向权威链

```text
产品定义 → 领域模型 → 目标架构 → 实现对齐 → 当前代码与证据
```

- 上游决定下游必须满足什么，下游只报告承载、偏差和证据，不能反向改写上游。
- 源码、测试、文件布局和历史建设事项只能作为调查证据，不能因为“现在就是这样”而升级成产品、领域或架构事实。
- 智能编码代理负责调查、比较、形成有依据的语义候选；项目负责人负责确认产品含义和重大取舍；程序只校验结构、身份、引用、版本、状态和确定性规则。
- 不静默修改已确认内容。替换、拆分、合并或废止时保留稳定身份、修订关系和新旧事实谱系。

## 建立或修订产品定义

1. 从用户、待解决问题和预期结果开始，不从已有功能清单或源码目录倒推产品目的。
2. 明确产品能力、范围、非目标、约束、成功判断、交付阶段和未决决定。每项能力必须能追溯到用户问题和预期结果。
3. 对每项能力检查正常使用、阻断、纠正和取消；确实不适用时说明原因，不能用空项代替判断。
4. 把当前已实现内容与未来目标分开。交付阶段只说明当前承诺和未来候选，不把未来设想冒充当前可用能力。
5. 范围、非目标、重大约束或成功判断仍有真实未决决定时保持草稿；一次只向项目负责人提出一个会实质改变方向的问题，并说明推荐、影响和不处理后果。

产品定义回答“为什么建设、为谁建设、解决什么问题、承诺哪些能力和边界”，不写模块、接口、数据库、测试命令或实现路径。

## 建立或修订领域模型

1. 绑定精确且已确认的产品定义。产品定义未确认或引用不明确时，停止领域定档。
2. 盘点当前领域目录、集合、来源和现行事实，只读取判断所需分支，不根据目录名推断领域边界。
3. 校准统一语言：一词多义时提出精确候选词；新说法与已确认定义冲突时明确指出，不悄悄改写。
4. 为每项产品能力建立完整领域解释，至少覆盖参与者与决定权、正常情形、阻断情形、纠正情形、取消情形，以及前置条件、触发、步骤、结果和后置条件。
5. 识别有身份对象、值对象、生命周期、事件、规则和不变量，用异常与边界情形检验，不只描述顺利路径。
6. 按业务决定权、语言、规则和一致性边界划分领域边界，再定义边界间方向、合同和外部系统责任；包、目录、类和部署单元不能直接充当领域边界。
7. 检查每项事实的产品能力归属、作用范围、显式依赖和闭包。范围关键未知必须在定档前解决，或由产品定义明确排除。
8. 候选修订列出新增、澄清、替换、拆分、合并和废止，以及对目标架构、实现对齐和在途事项的影响。

领域模型回答“产品范围内哪些业务含义必须成立”，不写源码路径、框架、数据库、测试回执、当前实现状态或某个事项的实施方案。

### 在讨论中澄清含义

先用已确认事实判断新说法：它可能只是换了措辞，也可能指另一个概念、另一个上下文，或提出了业务规则变更。能从现有来源确定的含义直接解释；只有不同解释会改变责任、行为或范围时，才提出一个具体决定，并说明建议及影响。

- 在同一上下文中选择清楚的规范称呼，定义先简述“是什么”，再说明必要边界和易混概念。不同上下文里的同名词可以各有含义，不能为统一字面而合并事实。沿用现有 `term`（术语）事实及其作用范围；易混词可以在定义中解释，不增加合同未支持的别名字段。
- 用当前能力中能区分两种解释的具体情形检验模型，例如同一对象在操作前后由谁负责、条件不满足时什么必须保持、纠正后能否继续。把构造的情形明确标为假设，不能当作已发生事件或新需求。已有场景足以作出判断时停止扩展，不把所有概念变成固定问卷。
- 用户说法与代码不同，先分别说明已确认含义、观察到的行为和差异，再按实现对齐的问题分类处理。已确认规则清楚而代码偏离时，报告实现偏离；目标确需改变时才形成上游候选。证据不足时保留未知，不能为了与代码一致而改写领域定义。

以下是处理方式示例，事实和路径仍以当前项目为准：

| 讨论中的情况 | Agent（智能编码代理）的处理 |
|---|---|
| 用户说“维修工单处理完了”；模型已有“已解决”和“已关闭”，分别对应维修完成与报修人验收 | 先查当前记录并解释已满足哪一项；只有验收决定确实缺失时才询问。不要直接新增含糊的“完成”状态。 |
| 客服上下文的“客户”指实际使用者，结算上下文的“客户”指付款组织 | 分别保留定义和作用范围，澄清双方交换的是哪种身份及由谁维护；不要因为同名就合并为一个事实。 |
| 已确认规则允许取消部分订单项，但当前实现只能取消整单 | 报告实现与规则的差距，把实现位置留在调查或对齐证据中；不要把领域规则改成“只能整单取消”。 |
| 讨论是否允许重开工单，但尚不清楚重新处理会不会撤销原验收 | 用“关闭后同一故障再次出现”这个假设比较重开旧工单与另建关联工单的后果，只询问影响历史和责任的未决选择，不预先采用任一方案。 |

### 把澄清整理为现有候选

在已授权起草的范围内，及时把确定的解释整理进当前候选的正式来源位置，并保留当前确认修订的可追溯性。语义不变的澄清沿用事实身份；替换、拆分、合并按现有谱系规则处理。一次澄清答复不代替下方的完整候选确认；只读分析时只说明建议，不写文件。

不另建可独立修改的 `CONTEXT.md` 或 `CONTEXT-MAP.md` 作为第二套权威，也不因缺少这些文件推断项目只有一个上下文。阅读版词汇表从选定的正式模型解释含义，不能反向覆盖来源。仍按上文检查完整模型，不能用词汇表代替场景、规则、生命周期和决定权。

需要长期保留的架构取舍按项目工程政策和本次评估处理，优先检查是否已有适用 ADR（架构决定记录）。说明决定、理由、关键替代方案及后果，篇幅以足够理解为准；不要为每次术语澄清新建 ADR。变更难以逆转、理由无法从实现看出或替代方案值得保留，都是调查线索，不是可以跳过现有 ADR 要求的三个必备条件。

## 建立或修订目标架构

1. 绑定精确且已确认的领域模型；领域覆盖不完整时，先补领域，不用架构猜测补语义。
2. 为每个目标模块定义负责什么、不负责什么、稳定接口、允许依赖和所承载的领域事实。
3. 定义模块关系、跨边界合同、外部系统边界和全局约束；关系必须有方向且无循环，禁止使用“共同负责”掩盖归属不清。
4. 对每项现行领域事实给出明确处置：由哪个目标责任承载、仅作为全局约束、由外部系统负责，或为何无需独立实现。
5. 定义实施阶段、进入条件、完成条件和允许的过渡状态。未来阶段不能反向成为当前代码免责理由。
6. 用正常协作、依赖受阻、偏差纠正和阶段取消场景检查架构是否闭合；无法唯一归属或无法沿允许关系完成的行为必须阻断定档。

目标架构回答“未来应该由谁以什么稳定边界承载领域事实”，不记录当前文件路径、当前完成度或验证回执。

## 建立或修订实现对齐

开始写四份底账前，读取
[implementation-alignment-artifact-contracts.md](implementation-alignment-artifact-contracts.md)
（实现对齐从属产物精确结构合同），使用公开的精确版本、字段和枚举，不得猜写。

1. 绑定精确产品、领域、目标架构修订和不可变代码版本；对工作树调查必须明确它不是已定档版本。
2. 逐项记录当前行为文件的唯一归属、实际直接依赖、目标责任实现程度、领域事实处置、证据和限制。
3. 将发现分类为上游语义缺口、目标架构缺口、实现偏离、证据不足或无法确定。只有前两类可以提出上游修订候选，不能直接回写上游。
4. 可机械确定的未归属行为、未声明依赖、循环、越过阶段或证据断裂必须显式失败；语义是否正确仍由智能编码代理审查并由项目负责人确认。
5. 建设需要改变产品、领域或目标架构时，停止依赖旧目标，先确认精确上游修订，再重做所有受影响的下游对齐。

实现对齐回答“当前实现与已确认目标相比是什么情况”，它是可更新的下游证据，不是新的产品、领域或架构权威。

## 长期权威确认规程

- 普通建设事项的方向、完整工程方案、实际结果三个确认点保持不变；长期权威首次定档或实质变更是独立决定，不能伪装成第四个普通事项确认点，也不能调用普通事项的 `strixnova confirm`（Strixnova确认命令）代替。
- “独立”指每类权威的接受范围和精确修订不能互相代替，不要求机械增加对话轮次。五类候选同时完整且引用闭合时，用一份完整候选包集中展示，允许负责人在一条后续消息中逐类决定；不要把同一项目拆成五次几乎重复的等待。
- 现有项目只展示本轮实际发生内容变化的权威候选。已经判断为不变的权威继续沿用当前确认修订，不生成空修订、不展示候选卡、不请求重复接受；若方案把“不变”权威列为候选，实施前必须重规划。
- 上游权威发生变化时，实现对齐不能继续视为不变。编码前先形成一份绑定新领域与新架构修订的 `draft`（草稿），按当时真实代码记录未实现、部分实现和偏离；它不在此时取得上游语义确认。实施期间只刷新这份尚未确认的候选，实际结果接受后再由程序机械定档。这样既不让旧实现对齐污染新目标，也不要求负责人重复确认同一实现证据。
- 展示候选时用中文说明当前修订、相对已确认版本的精确变化、影响范围、仍有缺口和需要负责人决定的一件事，然后结束当前回复，等待用户后续消息。
- 用户接受澄清答案不等于接受随后形成的完整候选。按[确认规程](confirmation-and-cancel.md#long-term-authority-candidates)解释完整候选并保留后续答复；Agent 通过公开 `strixnova authority` 提交决定，程序写入确认状态、身份和日期。Agent 不手改确认元数据。
- 用户退回时保持原已确认修订有效，把纠正意见形成新候选；用户取消时保留现行权威与历史，不得把未确认候选变成事实。

## 控制用户负担与完成声明

- 先自行调查项目中可查明的事实，不让项目负责人提供文件位置、技术结构或工程方法细节。
- 只询问会改变产品范围、领域含义、决定权或架构边界的未决事项，一次一个；一旦范围内内容和关键未知能完整陈述，就停止扩展问题。
- 分别报告结构校验、语义审查、负责人确认和实现对齐。结构通过只证明机器可判断的合同成立，不证明语义正确；没有精确负责人确认时只能称为候选。
